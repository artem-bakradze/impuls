## Context

Зачем это нужно, описано в proposal.md, раздел Why. Ниже — текущее устройство, от которого отталкивается решение.

- `dailyEvaluation` (`apps/worker/src/jobs.ts`) каждое утро:
  1. запускает страховочные правила по прошлой оценке, если с неё был состоявшийся ход агента (`agentActedSince`);
  2. сохраняет новую оценку (классы и `borderlineSince`);
  3. запускает ход `daily_review`;
  4. если ход не состоялся — пишет «день правил» (`saveRulesDay`, служебный инсайт `RULES_DAY_CODE`) и запускает правила по новой оценке с `agentActed: false`. Тогда эксперименты стартуют без 7 дней ожидания (`packages/core/src/safety-net.ts`).
- Событийные ходы (модерация, итог эксперимента, настройки, запуск) идут через входящие события `enqueueAgentEvent`/`mergeEvents` (`agent-turn.ts`). Разбор недели — отдельный триггер `weekly_review`.
- Симуляция (`apps/worker/src/simulation-mode.ts`):
  - бегущий таймер `tickSimulations` со скоростью и статусами `running` и `until_decision`;
  - шаг `stepDay`: часы по одному через `advanceWorld`, с выходом после каждого хода агента, чтобы пульт видел прогресс;
  - «Начать заново» — `restartSimulation`, который удаляет данные прогона.
- Рынок воспроизводим по `seed`. В `packages/agent/src/policies.ts` уже есть `ReplayPolicy`, она проигрывает записанные вызовы через текущие ограничители, но возвращает служебное итоговое сообщение.
- Журнал хода хранит триггер, контекст и вызовы с результатами (`ad-agent`, «Журнал агента»). У инсайта есть факты с ключами (`InsightFactRecord.key`) и `objectRef`.

## Goals / Non-Goals

**Goals:**
- поводы считает чистая функция в `packages/core` — детерминированно, с тестами на каждый повод;
- три исхода дня различаются явно: «ход состоялся», «повода не было», «решали правила»;
- история недели строится только из сохранённых записей и открывается одинаково в любой момент;
- повтор прогона без вызовов модели, с понятным расхождением.

**Non-Goals:**
- **Фоновый предрасчёт следующей недели.** Пока пользователь смотрит неделю N, мир уже ушёл бы в N+1. Тогда сводка, история и откат показывали бы будущее или работали бы против него. Вместо этого прогресс шага виден на пульте честно, день за днём.
- Новые рычаги агента и изменение ограничителей.
- Звук, конфетти и прочие эффекты сверх трёх сцен.
- Удаление колонки `speed` у записи симуляции в этом изменении: она перестаёт использоваться, а удалить её можно отдельной миграцией.

## Decisions

### 1. Поводы — чистая функция по находкам с устойчивыми ключами

`turnReasons(input)` в `packages/core` строит находки с ключами:

| Ключ | Что значит |
|---|---|
| `ineffective:ad:<id>`, `ineffective:direction:<id>` | объект неэффективен |
| `classified:ad:<id>` | объект вышел из обучения |
| `scale:direction:<id>` | у эффективной рекламы есть запас для прибавки |
| `borderline:ad:<id>` | пограничное объявление скоро получит страховочную проверку |
| `swing:direction:<id>:cpl:up` (и другие пары показатель/направление) | резкая разница с прошлой неделей |
| `hypothesis:<id>` | день проверки гипотезы |

Повод — находка, которой нет в находках последнего состоявшегося хода или которой не было в предыдущей оценке. Второе условие реализует «исчезла и появилась снова». Выход находки из «неэффективных» — отдельный повод «перестала быть неэффективной»: ключ был у последнего хода, а теперь его нет.

Пороги задаются константами рядом с ограничителями:
- запас для прибавки — те же 90% лимита, 3 дня с прошлой прибавки и не меньше 5% прибавки, что у страховочного масштабирования (функция переиспользуется);
- пограничное — серия `EXPERIMENT_DELAY_DAYS − 1` дней;
- резкая разница — 50% при не меньше 3 обращениях хотя бы в одном из периодов.

Альтернатива — дать модели решать, нужен ли ход. Отклонена: это опять вызов модели, и спека запрещает модели определять поводы.

### 2. Где хранятся находки

- Находки оценки — новое поле `findings` (jsonb) у записи оценки.
- Находки, которые видел ход, — в триггере хода (`{ kind: "daily_review", reasons, findings }`). Триггер уже сохраняется в журнале хода, так что новая колонка у ходов не нужна.

Последний состоявшийся ход берётся из журнала. Событийные ходы тоже видят находки последней оценки, поэтому их находки считаются увиденными.

### 3. Три исхода дня и страховочные правила

`dailyEvaluation` после оценки:
- **есть поводы и агент решает** → ход с поводами;
- **поводов нет и агент включён и решает** → служебный инсайт `QUIET_DAY_CODE` (по образцу `saveRulesDay`), модель не вызывается;
- **агент выключен, недоступен или за лимитом** → как сейчас, «день правил» и правила по новой оценке с `agentActed: false`.

Признак `agentActedSince` для правил по прошлой оценке заменяется на «прошлый день закончился ходом или был тихим». Тогда в тихий день правила ждут агента ровно так же, как после хода: эксперимент через 7 дней, отключение через 24 часа. Недоступность агента для инцидента считается только по запущенным ходам.

Альтернатива — в тихий день не запускать правила вообще. Отклонена: брошенная агентом находка, например последнее объявление без замены, никогда бы не дошла до правил.

### 4. Лента: тихие дни

`insights-model` превращает инсайт `QUIET_DAY_CODE` в `DayReviewModel` с `quiet: true` без сообщения. Подряд идущие тихие дни без других инсайтов сворачиваются через уже существующее поле `from`, как дни правил с одной причиной.

### 5. Симуляция: шаг недели вместо таймера

- **Новое действие `step_week`** устроено как `stepDay`: цель — `+7 дней` или конец сценария; статус `stepping`; выход после каждого хода, чтобы пульт показывал «Сервис разбирает 10-й день…». В статус пульта добавляются `stepKind`, `stepTo` и номер недели.
- **Убирается:** `tickSimulations`, ticker в `main.ts`, действия `resume`, `pause`, `until_decision`, `speed`, статусы `running` и `until_decision`.
- **Миграция данных:** статусы `running` и `until_decision` переводятся в `paused`.
- **Скорость шага:** искусственной задержки нет, шаг идёт так быстро, как считается. Ограничение 30 секунд на неделю без модели проверяет интеграционный тест, заменяющий `simulation-speed.integration.test.ts`.
- **Окна шагов** хранятся в новом поле записи симуляции `steps` (jsonb): `{ kind, from, to }[]`. Их немного, около 9 за 60 дней. Номер недели — порядковый номер шага `week`. «+1 день» добавляет окно `day`, у которого нет истории.

Альтернатива — оставить таймер и добавить «неделю» как ещё одну кнопку. Отклонена: два способа двигать время ломают историю недели (неделя посреди бегущего времени) и требование «время стоит между шагами».

### 6. История недели: модель на сервере, анимация на клиенте

`buildWeekStory(businessId, window)` в `apps/web/src/lib/simulation-screen.ts` собирает:
- статистику по объявлениям за окно (`store.stats`) и классы последней оценки в окне;
- правду сценария (`scenarioTruth`);
- ходы и инсайты окна, тихие дни свёрнуты;
- изменения окна без подстроек `budget-guard` (`isBudgetAdjustment`) с их ответами ограничителя и откатом;
- точку сравнения с контрольным прогоном на конец окна.

Подсветка строк — по объекту из ключа факта, а если его нет — по `objectRef` инсайта.

Компонент `WeekStory` проигрывает сцены по таймлайну примерно на 8–12 секунд: CSS-переходы и `requestAnimationFrame` для счётчиков. Есть кнопка «Показать сразу». При `prefers-reduced-motion` сразу рисуется итоговое состояние. Компонент ничего не пишет и не вызывает API, кроме существующего отката. Тесты рендерят итоговое состояние.

Альтернатива — генерировать «рассказ недели» моделью. Отклонена: тексты должны проходить проверку фактов, а спека запрещает придумывать текст.

### 7. Повтор прогона на `ReplayPolicy`

При «Начать заново» → «Повторить» до удаления данных в поле записи симуляции `replay` (jsonb) копируются:
- ходы прогона в порядке выполнения: триггер, виртуальное время начала, вызовы, итоговое сообщение;
- действия владельца: виртуальный час, команда, объект.

`simulationWorld` подставляет в контекст мира `ReplayPolicy` из этого источника. Политика возвращает записанное итоговое сообщение и `usage: null`, поэтому затраты нулевые.

Расхождение наступает, когда:
- следующий ход по виртуальному времени или триггеру не совпадает с записанным;
- записанный вызов отклонён, хотя в исходном прогоне был принят;
- действие владельца не совпадает с записанным в тот же виртуальный час.

После расхождения в записи ставится `replay.diverged = true`, мир дальше берёт обычный runtime агента, а пульт один раз показывает сообщение (флаг `replay.notified`). «Повторить» доступно, если в прогоне был хотя бы один ход на модели (поле `model` журнала хода). «Прогнать заново» очищает `replay`.

Альтернатива — снимок базы и откат к нему. Отклонена: повтор должен проходить через текущие ограничители и давать новые записи с той же логикой, а снимок обходит исполнитель команд.

### 8. Web и API

- `/api/simulation` принимает `step_week`, `step_day`, `restart` с `mode: "repeat" | "fresh"`, `extend`, `go_real`.
- `SimulationBar`: «Прожить неделю» (или «Прожить оставшиеся N дней»), прогресс шага, «Начать заново» с выбором, меню «+1 день» и «Запустить по-настоящему».
- После `step_week` браузер переходит на `/simulation?week=N`.
- Сводка: «Прожить первую неделю».
- Тексты шага 6 мастера и выбора симуляции: без «месяца за 5 минут» и скорости, «каждая неделя — один шаг».

## Risks / Trade-offs

- **[Агент реже сам смотрит разрезы, минус-фразы и устройства]** → разбор недели по-прежнему смотрит их каждую неделю. Перед включением сравнить поведение на прогоне `pnpm eval:agent`: он платный, только по явному запросу. Если на сценариях аналитика станет хуже, добавить повод «разрез не смотрели 7 дней».
- **[Пороги поводов подобраны на глаз]** → константы в `core`, unit-тесты на границы; подстроить после eval и прогонов симуляции.
- **[Регрессия сроков страховочных правил]** → BDD на каждый исход дня: тихий день, ход, агент недоступен. Тест «неделя без поводов» проверяет, что эксперимент не стартует раньше 7 дней.
- **[Повтор расходится из-за недетерминизма вне рынка: время, UUID, порядок]** → сравнение идёт по виртуальному времени, триггеру и командам, не по идентификаторам. Тест «точный повтор» на тестовой политике в CI.
- **[Шаг недели с моделью идёт минуту-две]** → прогресс день за днём на пульте и ход агента в статусе. Шаг идёт на сервере, даже если вкладку закрыли.
- **[Убран непрерывный режим]** → это осознанное изменение спеки (**BREAKING** для пульта), e2e и тесты пульта переписываются.

## Migration Plan

1. Миграция Drizzle:
   - `evaluations.findings jsonb null`;
   - `simulations.steps jsonb not null default '[]'`;
   - `simulations.replay jsonb null`;
   - `update simulations set status = 'paused', last_tick_at = null where status in ('running', 'until_decision')`.

   Проверить SQL на отсутствие удалений.
2. Выкатить worker и web вместе: старый web вызывает удалённые действия пульта, поэтому API отвечает понятной ошибкой «Обновите страницу».
3. Откат — откат кода. Новые поля необязательны, старый код их игнорирует. Запущенные симуляции после отката стоят на паузе.
