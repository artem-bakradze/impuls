## Context

Мотивация — в proposal.md. Текущее состояние, которое определяет подход:

- `DIRECT_API_MODE` принимает `simulator | sandbox | production` в worker (`apps/worker/src/config.ts`) и web (`apps/web/src/lib/config-check.ts`). Worker в любом режиме, кроме `simulator`, падает с «адаптер не реализован» (`apps/worker/src/main.ts`). Плашка тестового режима показывается при любом режиме, кроме `production`.
- Адаптер `packages/platforms/src/yandex-direct` написан и покрыт тестами на подменённом HTTP, но с настоящим Директом не проверялся. Данные, которых нет в контракте, он получает через хуки `resolveAdTarget` (группа и ссылка) и `resolveAverageCpaParams` (цель и ЦСО). Канал всегда «Поиск»: `Network: SERVING_OFF`. Регион группы в контрактном тесте зашит как `RegionIds: [225]` (Россия).
- `NewCampaign` содержит только имя, лимит, стратегию и мониторинг. `launchAds` в worker передаёт канал направления в БД, но не в площадку. Ключевых фраз и ссылки на посадочную страницу в плане запуска нет.
- Контрактный тест (`yandex-direct.contract.test.ts`) ходит в песочницу по `DIRECT_SANDBOX_TOKEN`.
- OAuth-приложение «Импульс» (ClientID `56df642386ba4b89b3df0c7b11eb30e2`) имеет тип «Для доступа к API или отладки», права `direct:api` и `metrika:read`, а его адрес возврата зафиксирован на `https://oauth.yandex.ru/verification_code`. Заявка на доступ к API для него подана 29.10.2026 и не одобрена: API отвечает ошибкой 58 «Незавершенная регистрация».
- Тестовый аккаунт — `artembakradze`. Отдельный аккаунт пользователь создавать не стал, в нём могут быть настоящие кампании.
- В API Директа v5 геотаргетинг группы задаётся только списком регионов `RegionIds` (метод `AdGroups.add`). Полей для радиуса или точки там нет.

## Goals / Non-Goals

**Goals:**
- Разработка, CI и staging полностью работают без Директа.
- Совместимость с боевым API проверяется без показов и расходов, и тесты физически не могут задеть чужие кампании в тестовом аккаунте.
- Контракт площадки несёт всё, что нужно для запуска кампании в Директе, без хуков, специфичных для адаптера.

**Non-Goals:**
- Генерация ключевых и минус-фраз и текстов (задачи 6.x `bootstrap-ad-autopilot-mvp`). Здесь контракт только принимает их.
- Проверка показов, статистики, модерации и баланса на настоящих данных. Это остаётся на пилоте (задача 13.3).
- Получение баланса аккаунта. В API v5 баланса нет, а `getBalance` адаптера по-прежнему сообщает «не поддерживается». Решается отдельно.
- Таргетинг по радиусу. См. решение 6.

## Decisions

### 1. Два режима: `simulator` и `production`
Значение `sandbox` удаляется из схем конфигурации worker и web. Zod-схема отклоняет его стандартной ошибкой перечисления, а сообщение дополняется подсказкой «sandbox is no longer supported: Yandex shut the Direct sandbox down on 2026-07-15; use simulator». Плашка показывается при `simulator`.
- *Альтернатива:* оставить `sandbox` как синоним `simulator`. Отклонена: это скрытый fallback, и он запрещён AGENTS.md.
- *Альтернатива:* staging на боевом API с пустым аккаунтом. Отклонена: staging нужен для демонстрации полного цикла со статистикой, а без бюджета боевой API её не даст.

### 2. Контрактные тесты: боевой API, черновики, страж на уровне клиента
Страж подключается к `DirectClient` как `guard` с двумя хуками: `before` видит каждый запрос и может его отклонить, `after` видит результат и запоминает ID созданных объектов и найденных черновиков с префиксом.
Тесты используют `DIRECT_CONTRACT_TOKEN` и `DIRECT_CONTRACT_LOGIN`. Безопасность обеспечивается не дисциплиной тестов, а обёрткой над `DirectClient`, через которую идут все запросы контрактного прогона:
- **Предварительная проверка до любых изменений.** `Clients.get` должен вернуть логин, совпадающий с `DIRECT_CONTRACT_LOGIN`, рублёвую валюту и не агентский тип. Ошибка 58 превращается в сообщение «заявка на доступ к API Директа не одобрена».
- **Запрещённые методы.** `moderate` для кампаний, групп и объявлений отклоняется до отправки запроса. Методы оплаты из API v4 Live не подключаются вовсе.
- **Только свои объекты.** Изменяющие методы (`update`, `suspend`, `resume`, `archive`, `delete`, `add` для дочерних объектов) пропускаются, только если их ID есть в реестре объектов, созданных этим прогоном, или если это черновик с префиксом `impuls-contract-`, найденный при уборке. Всё остальное отклоняется до отправки.
- **Уборка.** В `beforeAll` удаляются черновики `impuls-contract-*` от прерванных прогонов. В `afterAll` удаляются кампании этого прогона. Директ разрешает удалять кампании, которые не показывались.
- **Проверка в конце.** Список кампаний без префикса, снятый до прогона, сравнивается со снятым после: поля должны совпасть.

Дополнительно журнал запросов прогона проверяется на отсутствие токена, как и сейчас.
- *Альтернатива:* отдельный пустой аккаунт как единственная защита. Отклонена: пользователь выбрал аккаунт, где могут быть настоящие кампании. Кроме того, ошибку в логине конфигурации страж поймает, а отдельный аккаунт — нет.
- *Альтернатива:* только чтение (`get`) без создания черновиков. Отклонена: она не проверяет форматы `add` и `update`, а именно они чаще всего расходятся с документацией.

### 3. Пауза и возобновление на черновиках
Черновик кампании в Директе нельзя остановить: остановка применима к работающим кампаниям. Поэтому контрактный тест проверяет `suspend` и `resume` так: запрос уходит, ответ разбирается, а ошибка, которую Директ вернёт для черновика, сопоставляется с конкретным `PlatformError`. Фактическая остановка работающей кампании подтверждается на пилоте. Это ограничение записывается в комментарии теста и в `docs/testing.md`.

### 4. Два OAuth-приложения
- **Отладочное** — существующее «Импульс», тип «Для доступа к API или отладки». Служит только для ручного получения `DIRECT_CONTRACT_TOKEN`, в коде сервиса его ClientID не используется.
- **Пользовательское** — новое, тип для авторизации пользователей, права `direct:api` и `metrika:read`, адрес возврата `<APP_URL>/api/direct/oauth/callback` для каждого окружения. Его ClientID и секрет хранятся в `YANDEX_CLIENT_ID` и `YANDEX_CLIENT_SECRET`, обязательных для web при `DIRECT_API_MODE=production` (вместе с `APP_URL` и `TOKEN_ENCRYPTION_KEY`). Worker пока требует только `TOKEN_ENCRYPTION_KEY`: обновление токенов, которому нужен секрет приложения, остаётся в задаче 3.2 `bootstrap-ad-autopilot-mvp`.

Обмен кода на токен идёт в маршруте web. AGENTS.md разрешает web единственный внешний вызов: обмен OAuth-кода. `state` — случайное значение, сохранённое в БД вместе с ID пользователя и сроком 10 минут, удаляется при первом использовании. Токены шифруются AES-256-GCM (`TOKEN_ENCRYPTION_KEY`, общий для web и worker) уже здесь, потому что без этого callback нечего сохранять. Логин аккаунта остаётся пустым, пока worker не проверит аккаунт; обновление токенов и отказ агентским и не рублёвым аккаунтам — задача 3.2 `bootstrap-ad-autopilot-mvp`.

Доступ к API Директа одобряется для конкретного приложения. Если поддержка Директа подтвердит, что одобрение не переносится, на пользовательское приложение подаётся отдельная заявка. Это организационная задача 1.2.
- *Альтернатива:* одно приложение для всего. Невозможна: у отладочного типа нельзя изменить адрес возврата.

### 5. Расширение контракта `AdPlatform`
Таргетинг описывает направление и переходит в `NewCampaign`; посадочная страница нужна каждому объявлению и переходит в `NewAd`, чтобы объявления, созданные после запуска, не зависели от памяти адаптера. Своей группы у объявлений нет:

```ts
interface LeadGoal { goalId: string; targetCostPerLead: Kopecks }
interface Targeting { city: string; keywords: readonly string[]; negativeKeywords: readonly string[] }
interface NewCampaign { name; channel: Channel; weeklyLimit; strategyId; leadGoal?: LeadGoal; siteMonitoring; targeting: Targeting; schedule: string }
interface NewAd { campaignId; title; text; landingUrl: string }
interface CampaignPatch { …; strategyId?; leadGoal?: LeadGoal }
interface StrategyCapability { id; title; requiresLeadGoal: boolean }
```

- Адаптер Директа создаёт кампанию, затем ровно одну группу (`AdGroups.add` с `RegionIds` и `NegativeKeywords`), затем ключевые фразы (`Keywords.add`). Объявление он кладёт в единственную группу кампании, найденную через `AdGroups.get`. Хранить ID группы в БД не нужно.
- `channel: "search"` даёт `Search` со стратегией и `Network: SERVING_OFF`; `"network"` — наоборот. Для `"network"` ключевые фразы не обязательны: адаптер включает группе автотаргетинг (в API v5 — фраза `---autotargeting` через `Keywords.add`; точный формат подтверждает контрактный тест).
- `landingUrl` приходит без меток. Адаптер Директа дописывает `utm_source=yandex&utm_medium=cpc&utm_campaign={campaign_id}&utm_content={ad_id}`: Директ подставляет ID при клике, поэтому направление и объявление различаются без отдельного поля в контракте.
- Цель Метрики хранится у бизнеса (`businesses.lead_goal_id`, пока не заполняется: подключение Метрики — задача 7.3 `bootstrap-ad-autopilot-mvp`). Платформа объявляет `requiresLeadGoal` у стратегий, `guard()` получает `leadGoalStrategies` и `hasLeadGoal` и без цели отклоняет команду кодом `NO_LEAD_GOAL` до вызова площадки, поэтому отказ детерминирован и попадает в журнал хода. Executor передаёт площадке цель и текущую ЦСО.
- Хуки `resolveAdTarget` и `resolveAverageCpaParams` удаляются.
- Симулятор принимает те же поля и отказывает так же, как адаптер (нет фраз у поиска, нет цели у оплаты за обращения). Таргетинг и ссылки он хранит, но на «истинные» параметры они не влияют.
- Ключевые фразы до подключения генерации (`ad-creatives`) собираются из карточки: каждая услуга и услуга + город; минус-фразы — базовый список из спецификации `ad-creatives`.
- *Альтернатива:* методы `createAdGroup` и `addKeywords` в контракте. Отклонена: у направления всегда одна группа, а лишняя сущность в контракте усложнит второй адаптер и откаты.

### 6. Зона показа: регионы вместо радиуса
API v5 принимает только регионы (`docs/research/geo-targeting.md`). В контракт идёт город бизнеса (первая часть адреса), а адаптер Директа переводит его в регион типа `City` из справочника `GeoRegions`; неизвестный город — явная ошибка `UNKNOWN_CITY`. Регион — понятие конкретной площадки, поэтому в контракте его нет. Спецификации `business-onboarding` и `campaign-settings` обещают выбор радиуса на карте. Как точно перевести радиус в регионы (город целиком или районы Москвы и Санкт-Петербурга), решает задача 4.1. Если окажется, что радиус в Директе через API недостижим, интерфейс выбора зоны придётся менять отдельным изменением спецификации, а не тихо подменять в коде. До решения launch передаёт регион города бизнеса, а радиус остаётся только в БД и интерфейсе.

### 7. Собственный сайт обязателен, мини-сайт — после MVP
Каждое объявление в Директе должно вести на существующую страницу, а мини-сайт сейчас создаётся только в настройках после запуска. ТЗ требует аналитику «на своём сайте» пользователя, то есть исходит из наличия сайта. Поэтому шаг «Где вас найти?» требует ссылку на сайт, план запуска несёт её как `landingUrl`, а маршрут запуска дополнительно отказывает без сайта кодом `NO_LANDING_PAGE`. Ссылки на Карты и ВКонтакте остаются источниками данных о бизнесе.
- Форма мини-сайта в настройках скрывается; `packages/minisite`, публикация, команды `UpdateMiniSite`/`PublishMiniSite` и их тесты остаются как задел. e2e редактирования мини-сайта через настройки удаляется вместе с формой; e2e статической страницы и Lighthouse остаются, потому что проверяют сам пакет.
- *Альтернатива:* шаг мастера «Соберём вам страницу» с публикацией мини-сайта до запуска. Отложена: это расширение сверх ТЗ, требует публичного домена мини-сайтов в конфигурации и отдельного изменения спецификации.

## Risks / Trade-offs

- [Тесты идут в аккаунт, где могут быть настоящие кампании] → Страж на уровне клиента из решения 2, сравнение кампаний «до/после», запрет `moderate`. Ошибка в коде теста упирается в страж, а не в кампанию.
- [Заявка на доступ не одобрена или одобрена только для отладочного приложения] → Контрактные тесты падают с понятным сообщением. Разработка не блокируется, потому что идёт на симуляторе. Уточнение у поддержки вынесено в задачу 1.2.
- [Черновики не позволяют проверить паузу, модерацию и статистику] → Ограничение задокументировано (решение 3). Эти вещи подтверждаются на пилоте.
- [Баллы API тестового аккаунта] → Прогон занимает порядка сотни запросов. Тесты не запускаются по расписанию, только перед релизом и по запросу.
- [Регионы грубее обещанного радиуса] → Решение 6. Задача 4.1 даёт ответ до реализации запуска в боевом режиме.
- [Уборка удалит чужой черновик с префиксом `impuls-contract-`] → Префикс зарезервирован за тестами и описан в `docs/testing.md`. Сервис его не использует: кампании сервиса начинаются с `[Импульс]`.

## Migration Plan

1. Локальные `.env`, CI и staging переключаются с `sandbox` на `simulator`. Без этого worker и web не стартуют, и ошибка прямо называет замену.
2. В `.env.local` разработчика `DIRECT_SANDBOX_*` заменяются на `DIRECT_CONTRACT_*`. В текущей локальной копии это уже сделано.
3. После создания пользовательского OAuth-приложения его ClientID и секрет заменяют в `YANDEX_CLIENT_*` значения отладочного приложения.
4. Откат: изменение не трогает данные БД кроме новой таблицы одноразовых `state`. Её миграция обратима удалением таблицы.
