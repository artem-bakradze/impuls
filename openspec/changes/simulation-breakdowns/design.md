## Context

Мотивация — в proposal.md, требования — в `specs/simulation-mode/spec.md`.

**Как устроено сейчас:**
- **Окно и проверки.** Окно «Добавить статистику» (`PeriodDialog`) и web берут форму периода из `periodForm` (`apps/worker/src/simulation-period.ts`). Модуль чистый и импортирует из `@impuls/platforms` только типы, поэтому работает и в браузере. Там же `checkPeriod` и `suggestPeriod` («Заполнить примерно»).
- **Действие периода.** `livePeriod` (`simulation-mode.ts`) проверяет цифры ещё раз и вызывает `SimulatedPlatform.recordPeriod(dates, totals)`. Тот раскладывает итоги объявления по дням поровну в пределах лимитов и пишет ячейки с флагом `entered`. Шаг сохраняет `input` в JSON записи симуляции.
- **Разбивка.** `getBreakdown` строит строки только для ячеек, у объявления которых есть правда рынка (`AdTruth`). Он делит каждую ячейку отдельно (`splitTotals`) по весам `segmentCells` с учётом минус-фраз и корректировок часа. Внесённые ячейки пропускаются: в режиме «Симуляция» `truthFor` возвращает `null`.
- **Ход агента.** Разбор периода (`period_review`) идёт тем же путём, что ежедневный ход. Тестовая политика вызывает `analystLevers` для направлений не в классе «обучение». Инструкция разбора периода (`PERIOD_REVIEW_INSTRUCTIONS`, шаг 4) говорит, что разбивки может не быть.
- **Факты и ограничители.** Вердикт сегмента (`segmentVerdict`), фильтр запросов, факты разрезов и ограничители минус-фраз и корректировок — из `add-agent-analyst-stage1`, они не меняются.

## Goals / Non-Goals

**Goals:**
- разбивка внесённых цифр точная в целых числах: по дням и по сегментам сходится с итогами;
- в одном модуле — окно (строка-пояснение), сервер (запись) и «Заполнить примерно» (пересчёт);
- агент и тестовая политика видят разбивку тем же `get_breakdown`, без особого пути для симуляции.

**Non-Goals:**
- менять генерацию трафика по правде сценария, `splitTotals` для сгенерированных ячеек, сценарии eval и `SimulationDriver`;
- новые измерения: дни недели, часы, регионы — отдельным изменением;
- ручной ввод цифр по сегментам и настраиваемая доля ненужного запроса;
- миграция БД: всё новое лежит в JSON записи симуляции.

## Decisions

### 1. Отметки — рынок периода, а не цифры

`PeriodMarket = { junkQuery: boolean; phonesWorse: boolean }`.
- **Как приходит.** Действие периода принимает необязательное `market`. Без него обе отметки сняты — так шлёт прежняя открытая страница.
- **Что сохраняется в шаге.** `market` и настройки каждого направления в начале периода: минус-фразы и корректировки.
- **Отметки следующего окна** берутся из последнего завершённого шага. «Начать заново» и «Новая кампания» удаляют шаги, а с ними и отметки.

Альтернатива — отдельные поля бизнеса или записи симуляции для отметок. Отклонена: шаг уже хранит всё, что описывает период, а «Заполнить примерно» нужны отметки и настройки именно прошлого периода (решение 5).

### 2. Раскладку считает чистая функция, симулятор хранит готовые строки

`splitPeriod(direction, adTotals, market)` в `simulation-period.ts` отдаёт по объявлению строки за период: устройства и, для поиска, запросы. Каждая строка — показы, переходы, обращения и расход.
- **Где считается.** Worker вызывает её в `livePeriod` по настройкам кампании на начало периода (`getTrafficSettings`) и передаёт строки в `recordPeriod` вместе с итогами.
- **Как хранится.** Симулятор раскладывает строки по дням (решение 3) и пишет в ячейку `segments: { device: Row[]; query: Row[] }`. `getBreakdown` для внесённой ячейки суммирует её строки, для сгенерированной считает как раньше.
- **Чем пользуется окно.** Та же функция в браузере строит строку-пояснение под направлением.
- **Общие множители.** Множители корректировок (`impressionMultiplier`, `priceMultiplier`) и `phraseMatches` берутся из `simulator-segments.ts` через новый подпуть `@impuls/platforms/segments`. Он импортирует только `@impuls/core`, так что окно считает ровно так, как рынок автотестов.

Отклонённые альтернативы:
- **Хранить рынок периода как `AdTruth` и делить каждую дневную ячейку через `splitTotals` при чтении.** На малых дневных числах округление всегда отдаёт остаток самому крупному сегменту. Одно обращение в день каждый раз уходит телефонам, и за две недели компьютеры выглядят как «потратили без обращений». Ровная разбивка без отметок так не получится.
- **Хранить строки только за период и делить их на дни при чтении пропорционально.** Сложнее чтение. Окно агента в 14 дней режет периоды, так что суммы за день всё равно надо считать точно.

### 3. Целые числа: сначала период, потом дни

**Период.** Для каждой метрики итог объявления делится методом наибольшего остатка (`allocate`) по весам строк:

| Метрика | Вес строки |
|---|---|
| показы | `w` |
| переходы | `w` |
| расход | `w × цена` |
| обращения | `w × f` |

Затем строки выравниваются: обращений не больше переходов, переходов не больше показов, расход только у строк с переходами. Излишек переходит к строкам с запасом в порядке веса. Равные остатки делятся в порядке, сдвинутом на число из первой даты периода и id объявления: на равных весах остаток не достаётся из периода в период одному сегменту.

**Дни.** Итоги объявления по дням уже посчитаны `recordPeriod`. Дни идут по порядку, и итог дня делится между строками пропорционально тому, что у строки ещё осталось, тоже наибольшим остатком и не больше остатка строки. В последний день остатки строк в сумме равны итогу дня. Так сумма строк за день равна итогу дня, а сумма строки за дни — её итогу за период. Внутри одного дня строка может получить обращение без перехода, но строка за период и за 14 дней, покрывающие целые периоды, правила соблюдает. Агент видит строки только за период и за 14 дней.

### 4. Сегменты и их веса

**Устройства.** Доли показов телефонов, компьютеров и планшетов — 0,60 / 0,35 / 0,05. Это `DEFAULT_DEVICES` рынка автотестов.

| | Телефоны | Компьютеры | Планшеты |
|---|---|---|---|
| вес `w` | 0,60 × `impressionMultiplier(adj)` | 0,35 × `impressionMultiplier(adj)` | 0,05 × `impressionMultiplier(adj)` |
| цена перехода | `priceMultiplier(adj)` | `priceMultiplier(adj)` | `priceMultiplier(adj)` |
| `f` без отметки | 1 | 1 | 1 |
| `f` с «С телефонов обращаются хуже» | 1/4 | 1 | 1 |

Здесь `adj` — корректировка устройства. Для телефонов это корректировка телефонов, для компьютеров и планшетов — корректировка компьютеров, как в Директе и `segmentCells`. При одинаковой цене перехода обращение с телефона вчетверо дороже, чем с компьютера. Не втрое: тестовая политика снижает цену устройства, только если оно дороже другого больше чем втрое (`DEVICE_GAP`), а окно разреза в 14 дней не захватывает первый день периода. При ровно трёх разах решение зависело бы от округления.

**Запросы** — только у рекламы в поиске:
- **Основные.** Каждый основной запрос направления — с равной долей, `f = 1`.
- **Ненужный.** Самый короткий основной запрос плюс первое слово из списка «фото», «идеи», «отзывы», «что это», которого нет в основных запросах и которое не убирают минус-фразы кампании при запуске: «маникюр фото». Обычные минус-слова мастера («бесплатно», «вакансии», «обучение», «курсы», «своими руками») в список не входят: они отсечены с первого дня, и ненужный запрос с ними никогда бы не показывался. Выбор идёт по минус-фразам запуска, а не нынешним, поэтому запрос не меняется от периода к периоду, и минус-фраза, которую сервис добавил позже, его убирает. Его доля — 25% от `w`, `f = 0`. Если подходящего слова нет, отметка для этого направления недоступна.
- **Под минус-фразой.** Если минус-фраза направления совпадает с запросом (`phraseMatches`), у запроса `w = 0`, и его доля уходит основным запросам.

Устройства и запросы делят одни и те же итоги независимо: каждое измерение сходится с итогом само, как отдельные отчёты Директа.

### 5. «Заполнить примерно» пересчитывает долю обращений и цену перехода

Для направления по отметкам `M` и настройкам `S` считаются два множителя:
- множитель обращений `q(M, S) = (Σ w·f / Σ w)` по устройствам × (то же) по запросам;
- множитель цены `p(M, S) = Σ w·цена / Σ w` по устройствам.

**Объявление с прошлым периодом:**
- `cr = cr_прошлый × q(M_сейчас, S_сейчас) / q(M_прошлый, S_прошлый) × шум`;
- `cpc = cpc_прошлый × p(сейчас) / p(прошлый)`.

**Объявление без прошлого периода:** обычная доля обращений канала × `q(M_сейчас, S_сейчас)`.

Пример — ненужный запрос: до минус-фразы `q = 0,75`, после неё `q = 1`, доля обращений вырастает в 1,33 раза. Шум прежний, 0,85–1,15, поэтому подставленная цена обращения в следующем периоде всегда ниже. Это проверяемый сценарий «После минус-фразы дешевле».

Отметки и настройки прошлого периода берутся из его шага. У старых шагов их нет — тогда они считаются ровными.

### 6. Форма окна несёт всё для раскладки

`PeriodFormDirection` получает:
- `keywords` — основные запросы, только поиск;
- `negativeKeywords` и `deviceAdjustments` на сейчас;
- `junkQuery` — текст ненужного запроса или `null`.

`PeriodForm` получает `market` — отметки прошлого периода.

`periodForm` получает настройки колбэком, как и запас по лимиту: модуль попадает в браузер и не должен тянуть адаптер Директа. Колбэк — новая чистая функция `campaignTraffic(state, campaignId)` в `@impuls/platforms` рядом с `campaignRoom`. Она читает `settingsLog` и `settings` и отдаёт ещё и минус-фразы запуска: по ним выбирается ненужный запрос (решение 4). Шаг сохраняет и сам ненужный запрос. Сервер строит форму заново под блокировкой. Поэтому раскладка всегда идёт по настройкам на момент выполнения, а не по тем, что видело окно.

### 7. Агент и тестовая политика

`PERIOD_REVIEW_INSTRUCTIONS`, шаг 4: «Запроси `get_breakdown` по каждому направлению с расходом: по запросам — только для рекламы в поиске, по устройствам — для всех. Действуй по разрезам, как в ежедневном ходе; по сегменту «собираем данные» ничего не меняй». Версия блока — `2026-11-06.1`.

Тестовая политика уже вызывает `analystLevers` в разборе периода, её достаточно проверить BDD. Страховочные правила не меняются.

### 8. Окно

Блок «Что ещё было за эти дни» стоит между периодом и направлениями: две отметки (`Checkbox`) с подсказкой одной строкой под каждой. «Часть денег ушла на ненужный запрос» показывается, если в форме есть направление в поиске с `junkQuery`. Подсказка: «Например, «маникюр фото»: по нему переходят, но не обращаются».

Строка-пояснение под направлением считается `splitPeriod` по введённым в поля цифрам. Сумма строк ненужного запроса округляется до 10 ₽: «Около 1 050 ₽ из 4 200 ₽ — на запрос «маникюр фото», без обращений». При расходе 0 строки нет. На 360 px блок идёт столбцом.

## Risks / Trade-offs

- **[Ненужный запрос «собирает данные»]** При малом расходе запрос не набирает цели и остаётся «собираем данные», агент его не трогает. → Так и в Директе. Разбор говорит, что сервис ждёт данных. Сценарии BDD берут расход недели не меньше цели.
- **[Шум по основным запросам]** Без отметок цена обращения основных запросов отличается только округлением, но языковая модель может заговорить о «дорогом запросе». → Ограничитель не даёт минусовать слова основных запросов. Инструкция велит не действовать по «собираем данные». Сценарий «Без отметок разбивка ровная» проверяет тестовую политику.
- **[Строка за день]** Строка за отдельный день внутри периода может нарушить «обращений не больше переходов». → Агент читает только окна, покрывающие целые периоды. Требование сформулировано для строки за период. Юнит-тест проверяет строки за период и сходимость по дням.
- **[Рост JSON]** Состояние симулятора растёт: до 3 + N строк на ячейку объявления в день. → За 60 дней с 5 объявлениями и 10 запросами это около 4 тыс. строк из четырёх чисел. Допустимо для JSON-колонки, сжатие ячеек суммирует строки.
- **[Нагрузка на окно]** Окно становится сложнее, а `minimize-interface-load` просит меньше. → Две отметки одной строкой с подсказками, без таблиц. Пояснение — одна строка и только при отметке.

## Migration Plan

Миграции БД нет.
- Старые шаги без `market` и ячейки без `segments` читаются как раньше: без отметок и без разбивки.
- Откат: вернуть код. Лишние поля JSON прежний код не читает.
- Разрезы старых периодов не пересчитываются. Разбивка появляется с первого периода после выкладки.
