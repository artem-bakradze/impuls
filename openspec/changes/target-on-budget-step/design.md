## Context

Мотивация — в proposal.md, требования — в specs.

**Как устроено сейчас:**
- **Цель в базе.** `businesses.cso_mode` (`user` | `auto`) и `cso_value` в копейках. Worker читает их как `CsoSource`:
  - `{ kind: "user", goal }` — своя цель;
  - `{ kind: "auto", reference }` — автоматический подбор.
  `resolveCso` в `packages/core/src/cso.ts` не пересчитывает свою цель. Тексты агента и страховочных правил уже различают «вашу цель» и «цель, которую мы подобрали».
- **Сохранение мастера.** `saveOnboarding` в `apps/web/src/lib/server/business.ts` на каждом шаге пишет в строку бизнеса бюджет и цель. `goalKopecks` всегда пишет `auto` с ориентиром `interimAutoGoalRub(бюджет)`: бюджет / 30, округлённый до 50 ₽. Запуск (`POST /api/onboarding/launch` → `launchAds` в worker) не трогает цель: worker берёт то, что уже лежит в строке.
- **Черновик.** `OnboardingDraftSchema.budget = { monthlyBudgetRub }`; комментарий прямо говорит, что цель всегда подбирается автоматически.
- **Настройки.** «Цена обращения» в `SettingsView`: «Подбирайте сами» / «Укажу сумму», поле `InputNumber` (шаг 50 ₽), команда `SetGoal` через исполнитель. Тело запроса проверяет сумму `int, 1…1 000 000`.
- **Шаг запуска.** Правки из proposal («Уже сделано») есть в коде: `launch-step.ts`, `AdPreview.tsx`, `LaunchStep.tsx`, `Wizard.tsx`, компонентные тесты, BDD `launch-step.feature`, e2e `simulation.spec.ts`.

## Goals / Non-Goals

**Goals:**
- своя цель задаётся до запуска и действует с первого дня так же, как цель из настроек;
- никаких новых путей записи цели после запуска: после запуска цель меняется только командой `SetGoal`.

**Non-Goals:**
- подсказка или оценка цены обращения в мастере (спека её запрещает);
- ограничение своей цели относительно бюджета — в настройках его тоже нет;
- изменение формы цели в настройках и общий компонент для мастера и настроек;
- изменения worker, БД, агента и ограничителей.

## Decisions

**1. Поля в черновике, а не отдельный объект цели.** `budget` получает:
- `goalMode: "auto" | "user"` — по умолчанию `"auto"`;
- `goalRub: number | null` — целое, 1…1 000 000, по умолчанию `null`.

Старые черновики разбираются с этими значениями по умолчанию, поэтому открываются с «Подбирайте сами». Режим и сумма хранятся отдельно: при переключении на «Подбирайте сами» и обратно введённая сумма не теряется. Пустое поле при «Укажу сумму» — допустимое состояние черновика, которое шаг не пропускает дальше.
*Альтернатива:* `goal: { mode: "auto" } | { mode: "user"; rub }`, как в теле команды настроек. Отклонена: состояние «выбрал „Укажу сумму“, но ещё не ввёл» пришлось бы хранить вне черновика, и оно терялось бы при сохранении шага.

**2. Цель пишется при сохранении мастера, а не при запуске.** Чистая функция `goalSource(draft): CsoSource` в `apps/web/src/lib/onboarding.ts`:
- `user` с суммой → `{ kind: "user", goal: rub × 100 }`;
- иначе → `{ kind: "auto", reference: interimAutoGoalRub(бюджет) × 100 }`, а без бюджета ориентир 0, как сейчас.

`goalKopecks` в `business.ts` превращает её результат в `cso_mode`/`cso_value`. До запуска строку бизнеса никто, кроме мастера, не читает. Бюджет уже пишется так же: внешних действий нет, исполнитель команд нужен только после запуска.
*Альтернатива:* передать цель в `LaunchPlan`, чтобы worker поставил её командой `SetGoal` при запуске. Отклонена:
- в журнале появилась бы правка «Вы изменили цель» раньше «Реклама запущена»;
- понадобились бы изменения worker и плана запуска ради значения, которое и так лежит в строке.

**3. Проверка — там же, где остальные проверки шага 2.** `stepIssues(2, draft)` добавляет проблему `goal` с текстом «Укажите сумму или выберите «Подбирайте сами»», если выбрано «Укажу сумму» без суммы. Маршрут запуска уже отклоняет черновик с незакрытыми шагами (`firstIncompleteStep`, `stepProblems`), поэтому запуска без суммы не будет и при обходе страницы. Границы суммы проверяются в двух местах:
- поле: `min`/`max`;
- схема черновика: `PUT /api/onboarding` отклоняет сумму вне 1…1 000 000 ₽.

**4. Интерфейс — те же слова, что в настройках, без общего компонента.** В `BudgetStep` под пресетами бюджета:
- группа `role="radiogroup"` «Цена обращения» с кнопками-пресетами «Подбирайте сами» и «Укажу сумму»;
- при «Укажу сумму» — `InputNumber` с суффиксом «₽», `id="field-goal"` для прокрутки к ошибке.

Пояснение `data-testid="auto-goal"` становится двумя вариантами текста по `goalMode`. Форма настроек не трогается: правила проекта запрещают попутный рефакторинг, а общий компонент сэкономил бы десяток строк.

**5. Итог: цель — частью строки «Бюджет».** `LaunchStep` дописывает к `budgetCeilingText` «Цель — до N ₽ за обращение», только если выбрана своя сумма. Отдельной строки нет: цель задаётся рядом с бюджетом и меняется тем же «изменить» (шаг 2).

## Risks / Trade-offs

- [Своя цель выше половины месячного бюджета: объявления почти не выходят из «Собираем данные» (нужен расход от 2 × ЦСО), и страховочное отключение срабатывает поздно] → Так же, как со своей целью из настроек. Месячный потолок бюджета от цели не зависит, деньги сверх бюджета не тратятся.
- [Слишком низкая цель (например, 50 ₽): реклама быстро признаётся неэффективной] → Уже есть «Цель важнее освоения бюджета»: сервис показывает фактическую цену и предлагает «Поднять цель до N ₽». Цель из мастера идёт тем же путём.
- [Сохранение мастера после запуска перезаписало бы цель из настроек] → Мастер после запуска закрыт, а «Новая кампания» в симуляции начинает его с пустого черновика (`startNewCampaign` стирает и бюджет, и цель). Поведение то же, что с бюджетом сейчас.

## Migration Plan

Миграции БД нет: старые черновики читаются со значениями по умолчанию. Выкатывается только `web`. Откат — откат `web`: бизнесы, запущенные со своей целью, сохраняют её. Это обычное состояние, которое и сейчас бывает после настроек.
