## 2. Данные и контекст бизнеса (db, worker)

- [x] 2.1 Схема: `businesses.mode` (`direct` | `simulation`, по умолчанию `direct`) и таблица `simulations` (сценарий, начальное число, план запуска, `sim_now`, `started_at`, `ends_at`, `last_tick_at`, скорость, статус, состояние, контрольный прогон); сгенерировать миграцию и проверить SQL; методы `Store`/`PgStore` и in-memory; проверка — интеграционный тест миграции на чистой БД и pg-store тест чтения/записи симуляции
- [x] 2.2 Сценарии `scenarios.ts`: 5 сценариев (обычный салон, одно объявление без клиентов, пограничное объявление, конец месяца, правка в кабинете) с «правдой» по каналу и номеру объявления, «правдой» варианта A/B, событиями по дням, минимумом объявлений и сдвигом даты запуска; проверка — unit-тест: каждый сценарий валиден, минимумы считаются по плану запуска
- [x] 2.3 `contextFor(businessId)`: боевой контекст для `direct`; для `simulation` — `SimClock`, восстановленный симулятор, свой `CommandExecutor`, `IdlePolicy`, `TemplateCreativeEngine`; загрузка и сохранение состояния под замком `sim:<businessId>`; веб-задачи выполняются в контексте своего бизнеса; проверка — unit-тесты: команда и откат бизнеса в симуляции меняют только его симулятор и пишут историю с виртуальным временем, у бизнеса `direct` поведение прежнее
- [x] 2.4 Запуск в симуляции: веб-задача `launch` принимает режим и сценарий, создаёт строку `simulations`, назначает «правду» объявлениям по сценарию, сохраняет план для «Начать заново»; проверка — unit-тест запуска: кампании в симуляторе, запись «Реклама запущена», ни одного вызова боевой площадки

## 3. Время симуляции (worker)

- [x] 3.1 Вынести из `dispatchHour` обработчик часа бизнеса `runBusinessHour`; `dispatchHour` пропускает бизнесы в симуляции; проверка — существующие тесты диспетчера и BDD зелёные, новый тест: бизнес в симуляции не обрабатывается почасовым cron
- [x] 3.2 Тикер: цикл раз в секунду, `tryWithLock`, шаг по виртуальным часам с `advanceHour` и `runBusinessHour`, сценарные события, сохранение после каждого часа, остановки на `ends_at` и в режиме «до следующего решения», не больше 10 одновременно идущих симуляций на worker; проверка — unit-тесты на фиктивных реальных часах: скорость «1 день = 10 секунд» даёт 6 дней за минуту, «до следующего решения» встаёт на паузу после записи `safety_net`, перезапуск worker продолжает с сохранённого часа
- [x] 3.3 Управление: веб-задача `simulation_control` (`pause`, `resume`, `speed`, `step_day`, `until_decision`, `extend`, `restart`, `go_real`); `restart` и `go_real` удаляют данные бизнеса и, соответственно, перезапускают план или возвращают мастер на шаг 6 с черновиком; проверка — unit-тесты: `restart` без действий пользователя воспроизводит ту же историю и цифры, `go_real` сохраняет карточку, бюджет и объявления
- [x] 3.4 Контрольный прогон `simulation_baseline` при достижении `ends_at`: тот же сценарий и план без обработчиков сервиса, итог в `simulations.baseline`; проверка — unit-тест: итог посчитан, а расходы контрольного прогона не больше недельных лимитов запуска
- [x] 3.5 Изоляция: письма владельцу и команде не отправляются для бизнесов в симуляции, `agentEnabled = false` для правил; проверка — тест доставки уведомлений: событие бизнеса в симуляции остаётся на сводке без письма
