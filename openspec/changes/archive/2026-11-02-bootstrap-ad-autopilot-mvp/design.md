## Context

Проект создаётся с нуля, мотивация описана в proposal.md (раздел Why). Ограничения, которые определяют архитектуру:

- **Площадка**: единственная площадка MVP — Яндекс Директ API v5. Поведение агента и ограничителей проверяется на собственном симуляторе (`testing-harness`) (песочница Директа отключена 15.07.2026, см. `replace-direct-sandbox`). Кампании живут в аккаунте пользователя, поэтому их могут менять в обход сервиса.
- **Агент**: стратегии создаёт и оптимизирует агент на OpenAI Agents API (публичная бета). Это управляемый OpenAI контур с сессиями, событиями и function tools, которые выполняет наше приложение. Данные хранятся в США, Zero Data Retention нет. Из России API недоступен, а условия OpenAI допускают блокировку аккаунта при доступе вне поддерживаемых стран.
- **Пользователь**: владелец бизнеса с бюджетом 3–100 тыс. ₽ в месяц, то есть 5–50 обращений в месяц. Статистической мощности мало, и правила оптимизации и экспериментов рассчитаны на это (`optimization-engine`, `ab-testing`).
- **Бюджет**: непревышение должно гарантироваться даже при недоступности сервиса (`budget-guard`).
- **Закон**: 152-ФЗ — персональные данные хранятся на серверах в РФ. Маркировка рекламы — через встроенный Яндекс ОРД в аккаунте рекламодателя.
- **Команда**: небольшая. Нужен один язык во всём стеке и минимум инфраструктуры.

## Goals / Non-Goals

**Goals:**
- Одно TypeScript-приложение и один воркер с общей доменной моделью.
- Каждое изменение рекламы проходит через единый путь в одном месте — исполнитель команд в worker. Так история и откат получаются автоматически, а одновременные изменения не могут вместе нарушить бюджет.
- Все внешние побочные эффекты (площадка, LLM, письма, публикация мини-сайтов) выполняет только worker. web работает с БД и очередью.
- Ядро (классификация, ограничители, страховочные правила, бюджет, эксперименты) не зависит от площадки и одинаково работает с Директом и симулятором.
- Агент — заменяемый «мозг» за портом `AgentRuntime`. Безопасность рекламы и бюджета не зависит от качества, доступности и поведения агента и от того, какой провайдер за ним стоит.
- Состояние площадки не принимается на веру: сервис регулярно сверяется с Директом.

**Non-Goals:**
- Микросервисы, Kubernetes, отдельная шина событий.
- Режим реального времени: минимальная гранулярность решений — час для бюджета и сутки для оптимизации.
- Собственная модель атрибуции: используется атрибуция Директа.

## Decisions

### 1. Стек: TypeScript-монорепозиторий
- `apps/web`: Next.js (App Router) и Ant Design — интерфейс и API-роуты. web читает БД и ставит команды и задачи в очередь; к внешним сервисам обращается только для обмена OAuth-кодов.
- `apps/worker`: Node.js-воркер — расписание, обработчики задач, единственный исполнитель команд, ходы агента.
- `packages/core`: доменная модель, классификация, ограничители, страховочные правила, budget-guard, эксперименты — чистые функции без ввода-вывода.
- `packages/platforms`: контракт `AdPlatform` и адаптеры `yandex-direct` и `simulator`. Адаптер объявляет каталог своих возможностей, в том числе доступные стратегии.
- `packages/agent`: порт `AgentRuntime` с реализациями «OpenAI Agents API», «тестовые политики» и «воспроизведение записанных ходов»; порт `LlmClient` для разбора сайтов и генерации текстов.
- `packages/db`: схема и миграции (Drizzle ORM), PostgreSQL 16.
- `tests/bdd`: BDD-сценарии на русском (`# language: ru`, vitest-cucumber), по одному каталогу на capability.
- `e2e`: Playwright и агенты-персоны на OpenAI Agents API.

Правила работы с кодом (язык, No-Fallbacks, BDD, ошибки и логи) зафиксированы в `AGENTS.md` в корне репозитория.

*Почему*: один язык для продукта и тестов; у OpenAI SDK (`client.beta.agents`) и у Playwright есть TS-версии. *Альтернатива*: Python (FastAPI) для бэкенда и TS для фронта. Отвергнута: два языка и дублирование доменных типов.

### 2. Очередь, расписание и симуляция
Очередь и расписание — pg-boss на той же PostgreSQL. Задачи: ежечасный сбор статистики, контроль бюджета и сверка с площадкой, ежедневная оценка и ходы агента, проверка модерации, баланса и доступности сайтов, публикация мини-сайтов, рассылки.

- **Обработчики отделены от расписания.** Каждая периодическая задача — обработчик `(ctx: { clock, db, platform, agent }) → результат`. В проде обработчики вызывает pg-boss. В тестах их вызывает `SimulationDriver`: он двигает виртуальные часы по часу, вызывает наступившие обработчики по порядку и умеет пропускать их, моделируя отказ воркера. Только так выполнимы сценарии «30 дней за минуту» и «48 часов без воркера» — с настоящим расписанием их не смоделировать.
- **Часовые пояса.** Ежечасный диспетчер ставит задачи «в 06:00 по времени бизнеса» тем бизнесам, у которых наступил этот час, вместо отдельного расписания на каждый бизнес.
- **Повторы.** У задач-команд автоматических повторов нет (`retryLimit: 0`). Повторы вызовов Директа — только внутри адаптера по правилам `platform-integration`.

*Почему pg-boss*: не нужен Redis, задачи транзакционны вместе с данными. *Альтернатива*: BullMQ + Redis — лишний компонент без выигрыша на нашей нагрузке.

### 3. Команды: единственный исполнитель, журнал до вызова площадки
Любое изменение (`PauseAd`, `SetSpendLimit`, `UpdateSchedule`, `StartExperiment`, `PublishMiniSite`…) — это объект команды. Команды выполняет только worker. web ставит их в очередь, а агент, страховочные правила, `budget-guard`, сверка и откаты вызывают исполнитель внутри worker. Путь команды:
1. **Блокировка бизнеса**: сессионная `pg_advisory_lock(business_id)` на выделенном соединении. Команды одного бизнеса выполняются строго по одной; при падении воркера блокировка освобождается сама.
2. **Текущее состояние**: чтение из БД и сверка ожидаемого `before` с фактическим состоянием объекта на площадке. При расхождении команда отклоняется с кодом `STATE_CHANGED`.
3. **Проверки**: валидация, затем `guard()` и `budget-guard` по текущему состоянию. Команда урезается или отклоняется.
4. **Журнал до вызова**: запись `change_log` со статусом `pending` и отдельным коммитом. В ней `before`, желаемое `after`, автор, причина (`reason_code` + факты), ссылки на снимок и ход агента.
5. **Вызов адаптера площадки.**
6. **Результат**: `applied` с фактическим `after` или `failed` с ошибкой.

Зависшие `pending` (воркер упал между шагами 4 и 6) разбирает задача восстановления. Она читает объект на площадке и помечает команду `applied` или `failed`, а неожиданное состояние передаёт в сверку (решение 15).

Откат — это команда, построенная из `before`. Она проходит тот же путь, поэтому подчиняется бюджету и сама журналируется. Для каждого типа команды объявлены `isReversible` и `rollbackConsequences`.

*Почему*: требования `change-history` (запись каждого изменения, откат, «что стало после») выполняются одним механизмом. Блокировка закрывает гонку, при которой два действия по отдельности проходят проверку бюджета, а вместе — нет. Запись `pending` до вызова не даёт изменению оказаться в Директе, но не в истории. *Альтернатива*: отдельная очередь на каждый бизнес. Отвергнута: блокировка проще и одинаково покрывает задачи воркера и вызовы инструментов агента внутри хода. *Альтернатива*: полный event sourcing. Отвергнут как избыточный: состояние кампаний живёт на площадке, нам нужен журнал, а не реконструкция.

### 4. Объяснения: текст агента + проверка, шаблоны для кода
- **Действия агента**: текст объяснения пишет агент в обосновании вызова инструмента. Вместе с текстом передаются `reason_code` и ссылки на факты снимка. Валидатор извлекает из текста все числа и сверяет их с фактами (рубли — точно, проценты — с округлением до 1 п.п.), а также проверяет стоп-лист жаргона. При ошибке вызов отклоняется, и агент переписывает текст.
- **Страховочные правила, `budget-guard` и сверка**: текст собирается из шаблона по `reason_code`, шаблоны проверяются стоп-листом в CI.

*Почему*: агент объясняет свои решения живее шаблонов, а проверка гарантирует, что числа совпадают с данными (требование `change-history`). *Альтернатива*: только шаблоны и для агента. Отвергнута: агент может принимать решения, которых нет в фиксированном списке `reason_code`.

### 5. Структура кампаний и стратегия
Направление = «группа услуг × канал (Поиск / Сайты-партнёры)» = одна кампания Директа. Кампании сервиса помечаются префиксом имени `[Импульс]` и хранят соответствие ID в БД. Источник истины для принадлежности — БД, а не имя.

Все кампании создаются с мониторингом сайта (`ENABLE_SITE_MONITORING`, в Директе по умолчанию выключен): Директ сам останавливает показы, если посадочная страница не открывается. Дополнительно worker раз в 15 минут проверяет доступность посадочных страниц, чтобы предупредить пользователя.

Стратегию каждого направления агент выбирает из каталога, который объявляет адаптер площадки. Инструмент агента принимает ID стратегии из каталога, поэтому вторая площадка добавляет свои стратегии без изменения инструментов. Каждая стратегия каталога MUST иметь лимит расходов, который выставляет `budget-guard`. Стартовый каталог Директа:
- «Максимум кликов» с недельным лимитом (`WB_MAXIMUM_CLICKS` + `WeeklySpendLimit`);
- оптимизация конверсий по цели Метрики со средней ценой обращения, равной ЦСО, с тем же лимитом.

В инструкциях агента записана рекомендация: начинать с кликов и переходить к конверсиям после ≥ 10 обращений в неделю, так как конверсионным стратегиям на малых бюджетах не хватает данных для обучения. Ограничитель запрещает менять стратегию направления чаще раза в 7 дней. *Почему каталог, а не любая стратегия*: стратегии без лимита расходов ломают первый рубеж `budget-guard`.

### 6. Алгоритм budget-guard
- **Бюджет месяца** `B_m`: в первый месяц работы `floor(B × дни от запуска до конца месяца включительно / дни в месяце)`, далее `B`.
- **Каждый час**: `spent_month` (Reports, `IncludeVAT=YES`, сегодняшний день включительно).
- **Каждые сутки, после любой команды и после сверки с площадкой**: `maxFutureSpend = Σ по кампаниям (недельный лимит × число недель до конца месяца, неполная неделя = полная)`. Лимиты уменьшаются пропорционально до выполнения `spent_month + maxFutureSpend ≤ 0,9 × B_m`.
- **Пороги**: 80% → уведомление, 95% → `PauseAll(reason=budget_exhausted)` с автоматическим `ResumeAll` 1-го числа.
- **Проверка команд**: та же формула на состоянии после команды, внутри блокировки бизнеса (решение 3).

Резерв 10% и порог 95% покрывают задержку статистики и корректировки. Это проверяется симулятором (200 месяцев со сбоями). Цена гарантии: неполная неделя считается полной, поэтому в конце месяца часть бюджета может остаться неизрасходованной. Фактическая доля освоения меряется на симуляторе и пилоте.

### 7. Детерминированное ядро: состояние, ограничители, страховочные правила
Три чистые функции в `packages/core`:
- `classify(stats, ЦСО)` — классы эффективности. Результат входит в снимок хода агента.
- `guard(state, command) → allow | clamp(command') | reject(reason)` — ограничители `optimization-engine` и `budget-guard`. Вычисляются по текущему состоянию на момент выполнения внутри блокировки бизнеса, с учётом действий, уже выполненных в этом же ходе. Снимок начала хода для `guard` не используется: он нужен только как «факты решения» для проверки чисел в объяснении и для журнала.
- `safetyNet(state, agentActions24h) → Command[]` — страховочные правила. Запускаются через 24 часа после ежедневной оценки и делают то, что агент должен был сделать, но не сделал.

Пороги вынесены в версионируемую конфигурацию, версия журналируется. Детерминированность обеспечивается отсутствием ввода-вывода и случайности. *Альтернатива*: агент без ограничителей, только с промптом «соблюдай правила». Отвергнута: критерии приёмки 3 и 7 тогда становятся вероятностными.

### 8. A/B-тесты: A/B-сегменты Метрики, расчёт — Beta-Binomial
Разделение аудитории — через A/B-сегменты Метрики (тот же механизм, что «Эксперименты» в Директе): две копии направления, каждая таргетирована на свою половину сегментов. Лимит исходного направления делится пополам. Если для аккаунта сегменты недоступны, применяется запасной вариант: два объявления в одной группе. Он используется только для поисковых гипотез про текст, с пометкой «пониженная точность».

Расчёт: априорное распределение Beta(1,1) для конверсии клик → обращение, P(B > A) методом Монте-Карло (10 000 выборок, фиксированный seed от ID эксперимента — для детерминированности). Стоимость обращения сравнивается через конверсию с поправкой на среднюю цену клика варианта. *Альтернатива*: частотный z-тест. Отвергнут: на 5–20 конверсиях не даёт выводов в разумный срок и плохо объясняется пользователю.

### 9. Статистика и сверка
Таблицы фактов `stats_daily(campaign_id, ad_id, date, impressions, clicks, cost_vat, conversions_by_goal)` — из Reports API (`CUSTOM_REPORT`, `AttributionModels=AUTO`, что совпадает с кабинетом по умолчанию, часовой пояс аккаунта). Сегодняшний день хранится в `stats_intraday` и перезаписывается ежечасно. Последние 7 дней ежедневно перезагружаются целиком. Флаг `STAT` из сервиса `Changes` (решение 15) запускает внеочередную перезагрузку статистики кампании. Подтверждения клиентов — в `client_confirmations(week, count)`. Сверка с кабинетом — отдельная еженедельная задача, которая сравнивает агрегаты с независимым отчётом Reports и пишет отклонения в метрики.

### 10. LLM в продукте: порт `LlmClient`
Используется для двух задач:
1. **Извлечение карточки бизнеса** из HTML сайта или карточки — structured output по JSON-схеме карточки; незаполненные поля = `null`, а не догадки.
2. **Генерация объявлений, ключевых и минус-фраз** — structured output с длинами полей. После генерации — детерминированная проверка: длины, стоп-слова закона о рекламе, обязательное присутствие факта из карточки. Проверка повторяется до 3 раз, затем объявление отклоняется.

Реализация по умолчанию — OpenAI API. Вызовы выполняет worker через исходящий прокси (решение 12), без персональных данных во входе. Модель задаётся конфигурацией.

### 11. Тестовый контур
- **Симулятор** реализует `AdPlatform`. Стохастическая модель: показы ~ Poisson, клики ~ Binomial(CTR), обращения ~ Binomial(CR), задержка и корректировки данных, неравномерный расход внутри недели. Симулятор эмулирует сервис `Changes` и «ручные правки в кабинете», чтобы проверять сверку. Временем управляет `SimulationDriver` (решение 2).
- **BDD-сценарии** — бизнес-поведение из сценариев спецификаций в `tests/bdd/features/<capability>/*.feature` на русском. Шаги работают через API и `SimulationDriver`.
- **Сценарии ограничителей и бюджета** — тесты Vitest на `packages/core` и симуляторе. Вместо агента подставляются тестовые политики — реализации `AgentRuntime`: «бездействующий», «вредитель», «случайный». Так гарантии проверяются без LLM, быстро и бесплатно.
- **Воспроизведение записанных ходов** — ещё одна реализация `AgentRuntime`. Она прогоняет записанные ходы реального агента через новые версии ограничителей и показывает, какие вердикты изменились.
- **Eval агента** — настоящий агент через тот же `AgentRuntime` против симулятора на 20+ сценариях, со сравнением с «оракулом» и предыдущей версией. Запускается перед сменой модели или инструкций, а не на каждый PR: это дорого и недетерминированно.
- **Контрактные тесты** — против боевого API в тестовом аккаунте, только с черновиками, перед релизом и по запросу (`replace-direct-sandbox`).
- **E2E-персоны**: отдельные сессии Agents API (не продуктовый агент) с function tools-обёртками Playwright (`goto`, `click`, `fill`, `read_page` по дереву доступности). Агент получает только цель персоны и работает против окружения `web + worker + simulator`. Результат (дошёл / не дошёл, число шагов) проверяется детерминированно по состоянию БД, а не по словам агента.
- **LLM-судья** для текстов — отдельный прогон по шаблонам объяснений и экранам с фиксированной рубрикой.

### 12. Инфраструктура
Хостинг-провайдер пока не выбран (см. Open Questions). Приложение не зависит от конкретного облака и использует только стандартные интерфейсы:
- Docker-образы `web` и `worker`;
- PostgreSQL 16;
- S3-совместимое хранилище: фото и опубликованные мини-сайты;
- отправка email по SMTP;
- секреты через переменные окружения.

Локально и в CI всё это поднимается в docker-compose: PostgreSQL, MinIO вместо S3 (включая публичный бакет мини-сайтов), Mailpit вместо SMTP.

Требования к будущему хостингу:
- серверы с базой данных и файлами в РФ (152-ФЗ);
- управляемый PostgreSQL или возможность его развернуть с резервным копированием;
- S3-совместимое хранилище со статической раздачей и TLS для отдельного wildcard-домена мини-сайтов (решение 16);
- исходящий доступ к OpenAI API. Если хостинг в РФ — через HTTPS-прокси за её пределами (`OPENAI_PROXY_URL`). Это туннель CONNECT: узел прокси не расшифровывает трафик, не хранит ключей и не содержит кода приложения. Прокси решает только сетевую доступность, но не вопрос условий OpenAI (см. Risks).

Сборка — Docker-образы в GitHub Actions. Конфигурация через переменные окружения. `DIRECT_API_MODE=simulator|production` определяет площадку и плашку тестового режима.

### 13. Ошибки, повторы, логи и мониторинг
- **Ошибки API** — `{ code, message }`: стабильный код (`DIRECT_TOKEN_REVOKED`, `BUDGET_LIMIT_EXCEEDED`, `STATE_CHANGED`…) и понятный текст на русском. Перехват — только на границах: API-роуты, задачи воркера, обработчики инструментов агента.
- **Конфигурация**: обязательные параметры проверяются при старте каждого приложения по схеме; при отсутствии значения приложение не запускается. Значения по умолчанию — только для необязательных параметров и с документированием. `OPENAI_PROXY_URL` — необязательный и задаётся, если хостинг в РФ.
- **Повторы** — только идемпотентные, ограниченные и с записью в журнал (требование `platform-integration`); других автоматических повторов нет.
- **Логи** — структурированные, на английском, с ID бизнеса, команды и хода агента. Токены и персональные данные маскируются до записи.
- **Выключатели** — флаги в БД (`agent_enabled`, `automation_enabled`), глобальные и на бизнес. worker читает их перед каждой задачей и вызовом инструмента, поэтому изменение срабатывает в течение минуты без деплоя. Переключение — служебной командой CLI с записью в журнал.
- **Инциденты** — таблица `incidents` и канал оповещения команды. Источники: превышение бюджета, агент недоступен дольше 24 часов, зависшие `pending`, расхождение статистики больше 1 ₽, устаревший heartbeat.
- **Heartbeat**: обработчики `budget-guard`, сверки и диспетчера отмечают время последнего успешного выполнения. web отдаёт `/health`, который возвращает ошибку, если отметка старше 2 часов. Его опрашивает внешний сервис мониторинга вместе с доступностью web и домена мини-сайтов: если умер сам worker, тревогу поднимет внешний монитор.

### 14. Агент на OpenAI Agents API
- **Порт `AgentRuntime`**: `runTurn(trigger, snapshot, tools) → TurnResult`. Реализации: OpenAI Agents API (прод и eval), тестовые политики (CI), воспроизведение записанных ходов (регрессия ограничителей). Исполнитель команд и ядро не знают, какая реализация работает.
- **Ход = отдельная сессия** (`client.beta.agents.sessions`), окружение `none`: файлы и песочница агенту не нужны, он работает только через function tools. worker создаёт сессию, отправляет триггер и снимок событием `agent.session.input.message`, читает поток событий, выполняет вызовы инструментов и возвращает результаты. После завершения хода worker сохраняет журнал и удаляет сессию. Все соединения исходящие из worker, входящих от OpenAI нет.
- **Память** — заметки агента и история в нашей БД (`ad-agent`), а не контекст сессии. Поэтому ходы воспроизводимы, eval и прод работают одинаково, а в США не копятся данные. Инструкции агента и список инструментов версионируются в репозитории, версия записывается в журнал каждого хода.
- **Один ход на бизнес**: отдельная блокировка «ход» на бизнес, не связанная с блокировкой команд, поэтому команды пользователя выполняются и во время хода. События копятся в `agent_inbox` и забираются следующим ходом. Изменение цели, бюджета или настроек отменяет текущий ход средствами Agents API и ставит новый.
- **Инструменты** — function tools, выполняются в worker. Бизнес берётся из серверной привязки `turn_id → business_id`, ID объектов в аргументах проверяются на принадлежность бизнесу. Инструменты действий идут через исполнитель команд (решение 3), инструменты заметок — нет. Таймаут инструмента — 30 с.
- **Контекст по белому списку**: снимок и результаты инструментов сериализуются по явному перечню полей; поле вне перечня не уходит. Тест перехвата проверяет отсутствие персональных данных и токенов.
- **Отказоустойчивость**: ошибки `agent.session.failed` и таймауты хода (10 минут) завершают ход без новых действий. Реклама продолжает работать, `safetyNet` и `budget-guard` срабатывают по расписанию. Флаг `agent_enabled` (решение 13) отключает агента, не трогая ядро.
- **Затраты**: учитываются по usage каждого хода. При достижении месячного лимита на бизнес ходы не запускаются до следующего месяца.

*Почему Agents API, а не самописный цикл на Responses API*: OpenAI берёт на себя цикл вызовов инструментов, сжатие контекста и восстановление внутри хода, а мы пишем только инструменты и ограничители. *Цена*: бета-API, привязка к OpenAI и хранение данных в США. Компенсация — порт `AgentRuntime` с узким контрактом «триггер + снимок → вызовы инструментов» и eval-набор, который позволяет сменить модель или провайдера.

*Почему без отдельного сервиса-шлюза за рубежом*: персональные данные всё равно фильтрует worker, поэтому шлюз не добавляет защиты. Зато он хранил бы ключ OpenAI и видел бы данные в открытом виде за пределами РФ, а также требовал бы своего протокола с worker и отдельного деплоя. Прокси-туннель (решение 12) не видит ни ключа, ни данных.

### 15. Сверка с кабинетом Директа
- **Раз в час** `Changes.checkCampaigns` с меткой времени прошлой проверки, по кампаниям сервиса:
  - `SELF` — чтение кампании и сравнение с ожидаемым состоянием;
  - `CHILDREN` — `Changes.check` и чтение изменившихся групп и объявлений;
  - `STAT` — внеочередная перезагрузка статистики кампании.
- **Ожидаемое состояние** объекта — последнее `after` из журнала. На нём же основана проверка `before` в исполнителе (решение 3).
- **Изменения, влияющие на расход** (лимит, стратегия, включение кампании или объявления), передаются `budget-guard`: значения вне допустимого урезаются командой с автором «Сервис». Остальные изменения принимаются как текущее состояние.
- **Каждое обнаруженное изменение** — запись `change_log` с автором «Изменено в кабинете Директа» и `before`/`after`. Её можно откатить, как любую другую.
- **После простоя** worker выполняет сверку раньше остальных задач.

*Почему*: без сверки ручное повышение лимита в кабинете тихо ломает первый рубеж `budget-guard`, а откат восстанавливает устаревшее состояние. *Альтернатива*: полное чтение всех кампаний каждый час. Отвергнута: `Changes` дешевле по баллам API и сразу говорит, где искать.

### 16. Мини-сайты: статическая публикация
- Команда `PublishMiniSite` рендерит HTML и ресурсы из карточки бизнеса и шаблона и кладёт их в S3-совместимое хранилище. Раздача — статическим хостингом или CDN на отдельном регистрируемом домене `*.<домен-мини-сайтов>`, который не делит cookie с приложением.
- Счётчик Метрики и цели встраиваются при публикации.
- Публикация занимает ≤ 1 минуты: рендер, загрузка, сброс кэша.

*Почему*: реклама работает круглосуточно, и посадочная страница не должна зависеть от деплоев и падений приложения, иначе клики оплачиваются впустую. Статика быстрее (Lighthouse ≥ 90), а пользовательский контент не лежит на домене с сессиями приложения. *Альтернатива*: рендер мини-сайтов в `web`. Отвергнута по тем же причинам.

## Risks / Trade-offs

- [Условия OpenAI допускают блокировку аккаунта при доступе или предоставлении доступа вне поддерживаемых стран; России в списке нет] → юридическая проверка до глубокой интеграции (задача 0.7). Прокси решает только сетевую доступность, не договорную. Порты `AgentRuntime` и `LlmClient` позволяют сменить провайдера, а сервис безопасно работает без агента.
- [Agents API в публичной бете — контракт может меняться] → код работы с OpenAI изолирован в реализации `AgentRuntime`; контрактные тесты на записанных событиях; ядро работает без агента.
- [Agents API хранит данные в США, ZDR не поддерживается] → персональные данные не передаются (белый список полей и тест перехвата); сессия удаляется после хода.
- [Пользователь меняет кампании в кабинете Директа] → ежечасная сверка (решение 15), урезание лимитов `budget-guard`, запись в историю, проверка `before` перед каждой командой.
- [Падение worker посреди команды] → журнал `pending` до вызова площадки и задача восстановления.
- [Одновременные изменения одного бизнеса] → единственный исполнитель и блокировка бизнеса (решение 3).
- [Агент ошибается или галлюцинирует] → ограничители и `budget-guard` в коде по текущему состоянию, проверка чисел в объяснениях, страховочные правила, лимит 20 действий в сутки, журнал ходов.
- [Prompt injection через данные сайта или карточки бизнеса] → эти данные передаются агенту как данные, а не как инструкции; бизнес берётся из привязки хода; никакой текст не обходит `guard()` и `budget-guard`; сценарий-тест с инъекцией.
- [Недетерминированность агента затрудняет тестирование] → гарантии проверяются тестовыми политиками без LLM, качество агента — статистически в eval-наборе, изменения ограничителей — воспроизведением записанных ходов.
- [Стоимость модели на бизнес с бюджетом 3–15 тыс. ₽ может быть заметной] → компактный снимок вместо полной статистики, один плановый ход в сутки, объединение событий, месячный лимит затрат на бизнес; фактическая стоимость меряется в eval и на пилоте.
- [Консервативный расчёт бюджета оставляет часть бюджета неизрасходованной] → это цена гарантии; доля освоения меряется на симуляторе и пилоте; при необходимости уточнить модель недельного расхода Директа.
- [Посадочная страница пользователя недоступна] → мониторинг сайта в Директе останавливает показы, собственная проверка предупреждает пользователя.
- [Тихая остановка worker] → heartbeat и внешний монитор `/health`; лимиты на стороне площадки держат бюджет до восстановления.
- [Доступ к боевому API Директа выдаётся после модерации заявки, срок не контролируется] → подать заявку в первую неделю; вся разработка идёт на симуляторе, так что задержка блокирует контрактные тесты и пилот.
- [A/B-сегменты Метрики могут быть недоступны через API для части аккаунтов] → проверить на первой неделе (задача-спайк); запасной вариант с пометкой «пониженная точность».
- [Малые бюджеты → эксперименты часто заканчиваются «разницы не обнаружено»] → это честный и явно объяснённый исход. Порог 100 кликов на вариант и лимит 2 одновременных экспериментов не дают дробить трафик.
- [Справочник исходной ЦСО по нишам неточен] → используется только в режиме «подберите сами» и как подсказка при вводе цели; пересчёт после 20 обращений.
- [Пользователь ставит нереалистичную цель, например 250 ₽ при типичных 600–1 200 ₽ → сильный недорасход и мало обращений] → предупреждение при вводе цели, явная подпись о недорасходе на сводке и предложение поднять цель до фактической медианы; цель никогда не меняется без согласия пользователя.
- [Расходы ручных кампаний пользователя в том же аккаунте не контролируются] → явное предупреждение при подключении; бюджет сервиса считает только свои кампании.
- [Пользователь не отвечает на вопрос о клиентах → стоимость клиента неизвестна] → показываем стоимость обращения с честной подписью; интеграция с YCLIENTS — следующий этап.
- [LLM-персоны проходят интерфейс «умнее» людей] → обязательный юзабилити-тест с 5 реальными владельцами до пилота.
- [Симулятор не подтверждает критерии приёмки 3, 4, 6] → пилот 3–4 недели с реальным бизнесом и бюджетом; критерии фиксируются отчётом пилота.
- [Изменения API Директа] → контрактные тесты по расписанию и журнал запросов.

## Migration Plan

Миграции нет: новый сервис. План ввода в эксплуатацию:

1. **Стенд `staging`** с `DIRECT_API_MODE=simulator`.
2. **Боевой стенд** с `production` и закрытым списком пользователей (allowlist email).
3. **Пилот** с 1–3 бизнесами.
4. **Открытие регистрации.**

Откат релиза: предыдущий Docker-образ; миграции БД — только совместимые назад (expand → contract). Экстренные выключатели — флаги в БД (решение 13), без деплоя: `agent_enabled=false` отключает агента (страховочные правила и `budget-guard` продолжают работать); `automation_enabled=false` дополнительно останавливает страховочные правила и эксперименты, но не `budget-guard`. Мини-сайты при откате релиза продолжают работать: они раздаются статикой.

## Open Questions

- Конкретные значения справочника исходной ЦСО по нишам и регионам: собираются на этапе исследования (интервью со специалистами), и формат справочника от них не зависит.
- Источник прогноза обращений на шаге «Бюджет»: Forecast из API Директа (v4 Live) или собственная оценка по справочнику. Спецификация допускает оба варианта и запасной текст.
- Домен для мини-сайтов.
- Конкретная модель агента и месячный лимит затрат на бизнес: выбираются по результатам eval-набора и не меняют архитектуру.
- Запасной провайдер для `AgentRuntime` и `LlmClient` на случай потери доступа к OpenAI: выбирается по итогам юридической проверки (задача 0.7); архитектура от него не зависит.
- Канал оповещения команды (email, Telegram) и внешний сервис мониторинга: выбираются при развёртывании.
- Выбор хостинг-провайдера по требованиям из решения 12. Приложение не привязано к провайдеру, поэтому выбор не меняет ни спецификации, ни архитектуру; он нужен до развёртывания staging.
