## Purpose

Подключение рекламного аккаунта Яндекс Директа пользователя и все операции с кампаниями через прямой API Директа. Слой площадки изолирован, чтобы позже подключить вторую площадку.

## ADDED Requirements

### Requirement: Подключение аккаунта Директа
The system SHALL подключать собственный аккаунт Яндекс Директа пользователя через Яндекс OAuth с доступом к API Директа и Метрики. Токены MUST храниться в зашифрованном виде и обновляться автоматически. Агентские аккаунты и аккаунты в валюте, отличной от рубля, в MVP SHALL отклоняться с понятным объяснением.

#### Scenario: У пользователя нет аккаунта Директа
- **WHEN** пользователь авторизовался в Яндексе, но аккаунта Директа у него нет
- **THEN** система показывает пошаговую инструкцию со ссылкой на создание аккаунта и проверяет его появление при нажатии «Я создал аккаунт»

#### Scenario: Токен отозван
- **WHEN** запрос к API возвращает ошибку авторизации
- **THEN** система приостанавливает автоматические действия по этому пользователю, показывает на сводке «Потерян доступ к Яндекс Директу — подключите заново» и отправляет уведомление на email; кампании продолжают работать с последними настройками и лимитами в Директе

### Requirement: Данные для маркировки рекламы
The system SHALL перед первым запуском проверять, что в аккаунте пользователя заполнены данные рекламодателя для маркировки через Яндекс ОРД. Если площадка не предоставляет такую проверку через API, система SHALL показывать инструкцию со ссылкой на нужный раздел кабинета и обрабатывать соответствующие ошибки API.

#### Scenario: Директ отклонил запуск из-за маркировки
- **WHEN** API возвращает ошибку, связанную с данными рекламодателя или маркировкой
- **THEN** система показывает «Яндексу нужны данные о вашем бизнесе для маркировки рекламы» со ссылкой на раздел кабинета и повторяет запуск после нажатия «Готово»

### Requirement: Режимы песочницы и боевого API
The system SHALL поддерживать два режима окружения: песочница Директа (`api-sandbox.direct.yandex.com`) и боевой API. Режим задаётся конфигурацией окружения, а не пользователем. В режиме песочницы интерфейс MUST постоянно показывать плашку «Тестовый режим — реклама не показывается».

#### Scenario: Окружение разработки
- **WHEN** сервис запущен с конфигурацией песочницы
- **THEN** все вызовы API Директа идут в песочницу, а на каждой странице видна плашка тестового режима

### Requirement: Структура создаваемых кампаний
The system SHALL создавать в Директе для каждого «направления» отдельную кампанию. Направление — это пара «группа услуг × канал»; каналы — «Поиск» и «Сайты-партнёры» (РСЯ). Каждой кампании SHALL назначаться:
- зона показа;
- расписание по часам работы бизнеса;
- цели Метрики;
- лимит расходов, выставленный `budget-guard`;
- мониторинг доступности сайта: площадка приостанавливает показы, если посадочная страница не открывается.

Сервис SHALL сам проверять доступность посадочных страниц не реже раза в 15 минут и предупреждать пользователя. Все кампании, созданные сервисом, MUST помечаться так, чтобы сервис отличал их от кампаний, созданных пользователем вручную. Кампании, созданные не сервисом, MUST оставаться нетронутыми.

#### Scenario: В аккаунте уже есть ручные кампании
- **WHEN** у пользователя в Директе есть кампании, созданные не сервисом
- **THEN** система их не изменяет, не останавливает и не учитывает в бюджете сервиса, а на шаге подключения предупреждает, что их расходы не входят в бюджет сервиса

#### Scenario: Посадочная страница не открывается
- **WHEN** сайт пользователя перестал открываться
- **THEN** показы кампаний с этой страницей приостанавливаются мониторингом Директа, а сервис показывает на сводке «Ваш сайт не открывается — показы приостановлены, чтобы не тратить деньги впустую» и отправляет email

### Requirement: Надёжность вызовов API
The system SHALL соблюдать балльные и технические лимиты API Директа. При временных ошибках система SHALL повторять только идемпотентные запросы (чтение, а также изменения с проверкой текущего состояния перед повтором), не больше 5 попыток с экспоненциальной задержкой, записывая каждую попытку в журнал. После исчерпания попыток операция MUST завершаться явной ошибкой. Система SHALL записывать журнал всех запросов и ответов API не меньше чем за последние 3 суток (требование Яндекса к приложениям).

#### Scenario: Исчерпаны баллы API
- **WHEN** API сообщает об исчерпании баллов
- **THEN** система откладывает несрочные операции до восстановления баллов и выполняет операции защиты бюджета в первую очередь

### Requirement: Сверка с кабинетом Директа
The system SHALL не реже раза в час проверять, менялись ли кампании сервиса в обход сервиса — в кабинете Директа или самой площадкой, — и сравнивать фактические настройки с ожидаемыми. Изменения, которые могут увеличить расходы (лимит расходов, стратегия, включение кампании или объявления), MUST проверяться `budget-guard` и урезаться до допустимых. Остальные изменения SHALL приниматься как текущее состояние. Каждое обнаруженное изменение MUST записываться в историю изменений с автором «Изменено в кабинете Директа». Корректировки статистики, о которых сообщает площадка, SHALL вызывать перезагрузку статистики затронутых кампаний. После недоступности сервиса сверка SHALL выполняться раньше остальных задач.

Перед выполнением любой команды система MUST сверять ожидаемое состояние объекта с фактическим. При расхождении команда агента или страховочного правила MUST отклоняться, а при откате пользователю SHALL показываться, что изменилось, с выбором: вернуть сохранённое состояние или отказаться.

#### Scenario: Текст изменён в кабинете
- **WHEN** пользователь отредактировал текст объявления сервиса в кабинете Директа
- **THEN** при ближайшей сверке система принимает новый текст как текущий и записывает в историю «Текст объявления изменён в кабинете Директа» с «было → стало»

#### Scenario: Состояние изменилось перед командой
- **WHEN** агент ставит на паузу объявление, которое пользователь уже остановил в кабинете
- **THEN** команда не выполняется, агент получает причину «состояние объекта изменилось», а изменение из кабинета записывается в историю при сверке

#### Scenario: Корректировка статистики
- **WHEN** Директ сообщает о корректировке статистики кампании за прошлые дни
- **THEN** система перезагружает статистику этой кампании за затронутые дни, не дожидаясь ежедневной перезагрузки

### Requirement: Отслеживание модерации и баланса
The system SHALL не реже раза в час проверять статусы модерации объявлений и баланс аккаунта.

#### Scenario: Объявление отклонено модерацией
- **WHEN** Директ отклонил объявление
- **THEN** система показывает причину простым языком, создаёт исправленный вариант через `ad-creatives` и отправляет его на повторную проверку не более двух раз, после чего просит пользователя отредактировать текст

#### Scenario: Заканчиваются деньги на балансе
- **WHEN** остатка на балансе Директа хватит меньше чем на 3 дня при текущих расходах
- **THEN** система показывает на сводке «Пополните баланс в Яндекс Директе — денег хватит примерно на N дн.» со ссылкой на пополнение и отправляет email

### Requirement: Расширяемость площадок
The system SHALL работать с площадками через единый внутренний контракт: создание и изменение кампаний и объявлений, пауза и возобновление, изменение лимитов, получение статистики и статусов. Подключение второй площадки MUST не требовать изменений в ограничителях оптимизации, инструментах агента, защите бюджета, истории изменений и интерфейсе сводки. Возможности, которые различаются между площадками (например, доступные стратегии), SHALL объявляться адаптером площадки.

#### Scenario: Подключение второй площадки
- **WHEN** разработчик добавляет адаптер VK Рекламы, реализующий контракт
- **THEN** агент, ограничители, защита бюджета и сводка работают с её кампаниями без изменения своего кода
