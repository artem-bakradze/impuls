## Context

Мотивация — в proposal.md.

**Как устроено сейчас:**
- **Вход** — Auth.js (`apps/web/src/auth.ts`), сессия JWT на 30 дней. Провайдеры:
  - Google;
  - при `AUTH_TEST_LOGIN=enabled` — тестовый вход по почте и имени (Credentials).

  Колбэк `jwt` требует email и создаёт пользователя через `upsertUser({ subject, email, name })`. `subject` — `google:<id>` или `test:<email>`, хранится в `users.google_sub` (NOT NULL UNIQUE). `users.email` — NOT NULL.
- **Стартовая страница** — `app/page.tsx` и `LoginCard`: заголовок, абзац, четыре преимущества, макет продукта, кнопка через Google, оговорки, форма тестового входа.
- **Режим бизнеса** — `businesses.mode` (`direct` | `simulation`, по умолчанию `direct`). Пользователь выбирает его в мастере (`ModeChoice` в `SimulationChoice.tsx`). Страница отправляет `POST /api/onboarding/launch` с `{ simulation: true }`, и worker запускает `launchSimulation`. «Начать заново», «Новая кампания» и `go_real` возвращают `mode` в `direct`.
- **Пульт симуляции** — `POST /api/simulation`. Устаревшие действия отклоняются с `410 SIMULATION_ACTION_GONE` и текстом «Пульт симуляции обновился — обновите страницу». `go_real` вызывает `leaveSimulation`.
- **Email владельца** — нужен worker только для писем (`store.ownerEmail`). В симуляции писем нет. Уборка удалённых аккаунтов отбирает строки по `email NOT LIKE 'deleted-%@invalid'`.
- **Шапка** (`AppHeader`) выходит формой с `signOutAction` без подтверждения.
- **Тесты.** e2e входят тестовым входом (`apps/web/e2e/helpers.ts`), `simulation.spec.ts` выбирает симуляцию в мастере. BDD про «Запустить по-настоящему» — `simulation-mode/simulation.feature` и `insights/insights.feature`.

## Goals / Non-Goals

**Goals:**
- демо одной кнопкой, без персональных данных;
- режим бизнеса — свойство аккаунта, которое проверяет сервер;
- вход через Google нельзя пройти ни кнопкой, ни прямым запросом;
- простая стартовая страница в оформлении «Рекламы».

**Non-Goals:**
- общий лимит расходов на демо, лимит числа демо-аккаунтов, капча, уборка брошенных демо — задача в `production-rollout` (proposal.md);
- перенос демо в настоящий аккаунт;
- включение входа через Google обратно — отдельное изменение.

## Decisions

**1. Вид входа — колонка `users.kind`.** Миграция:
- добавляет `kind text NOT NULL` со значениями `google` | `test` | `demo`;
- заполняет существующие строки по префиксу `google_sub`: `test:` → `test`, остальное → `google`;
- делает `email` необязательным;
- добавляет проверку `CHECK (kind = 'demo' OR email IS NOT NULL)`, чтобы email не терялся у настоящих аккаунтов.

Колонку `google_sub` не переименовываем: она уже хранит общий `subject`. У демо он `demo:<uuid>`, uniqueness сохраняется.

Альтернатива — выводить вид входа из префикса `subject` без новой колонки — отклонена: правило режима зависело бы от формата строки, а проверку «email есть у всех, кроме демо» нельзя выразить в схеме.

**2. Демо-вход — Credentials-провайдер `demo` в Auth.js.**
- `authorize` без полей возвращает нового пользователя `{ id: "<uuid>" }`.
- Колбэк `jwt` переводит вход в аккаунт чистой функцией `accountFromSignIn` (`apps/web/src/lib/account-mode.ts`): для `demo` — `subject = demo:<uuid>`, `kind = demo`, без email и имени; для тестового входа email по-прежнему обязателен; другие провайдеры отклоняются.
- Кнопка «Демо-режим» — server action `signInAsDemo()` → `signIn("demo", { redirectTo: "/" })`. CSRF-защиту даёт Auth.js.
- Сессия — тот же JWT на 30 дней.

Пользователь с действующей сессией стартовую страницу не видит: `page.tsx` уже переадресует его на `homePath`. Значит, второе нажатие «Демо-режим» в том же браузере невозможно, а новое демо появляется только без сессии.

Альтернативы:
- общий демо-аккаунт — данные посетителей смешались бы;
- готовый пример-бизнес — владелец просит проходить мастер на своём бизнесе.

**3. Google выключен на уровне провайдеров.**
- Провайдер Google не подключается в `auth.ts`, поэтому прямой `POST /api/auth/signin/google` получает ошибку Auth.js, и сервис возвращает на стартовую страницу.
- `signInWithGoogle` удаляется.
- `AUTH_GOOGLE_ID` и `AUTH_GOOGLE_SECRET` убираются из обязательной конфигурации web (`config-check.ts`) и из `compose.yaml`.
- Кнопка в `LoginCard` — `aria-disabled="true"` вне формы, с `Tooltip` по наведению и фокусу и `aria-describedby` на скрытый текст подсказки. Атрибут `disabled` не подходит: у отключённой кнопки нет событий наведения и фокуса, и подсказку пришлось бы вешать на отдельную фокусируемую обёртку.
- Действующие JWT-сессии Google (только стенды) проверяются подписью `AUTH_SECRET`, поэтому работают до срока без провайдера.

Альтернатива — оставить провайдер и отклонять Google в колбэке `signIn` — отклонена: секреты нужны были бы для выключенной функции, а экран Google всё равно открывался бы.

**4. Режим определяет сервер по аккаунту.**
- Новая серверная функция `accountMode(userId)`: `demo` → `simulation`, иначе → `direct`. Её используют страница мастера (передаёт режим в `Wizard` пропом) и `POST /api/onboarding/launch`.
- Новая страница не отправляет режим.
- Запрос с `simulation: true` от аккаунта в режиме `direct`, или с `simulation: false` от демо, отклоняется: `409 WIZARD_OUTDATED`, «Мастер обновился — обновите страницу».
- Запрос без поля запускает режим аккаунта. Отсутствие поля у старой страницы значило «Директ»; у демо-аккаунтов старых страниц не бывает, а для аккаунта `direct` это и есть его режим.

Альтернатива — молча запускать режим аккаунта, игнорируя запрос, — отклонена: старая страница с выбранной «Симуляцией» у аккаунта тестового входа запустила бы настоящую рекламу.

Worker не меняет логику запуска. Задание `launch` с `simulation: true` по-прежнему запускает симуляцию; режим проверяет web до постановки задания. Web — единственный, кто знает аккаунт.

**5. Мастер без выбора режима.**
- `ModeChoice` удаляется, а с ним `SimulationChoice.tsx`, если в нём не останется ничего другого.
- `LaunchStep` и `Wizard` получают `mode` от страницы. Тексты кнопки, заметки «Что будет после запуска», подключения Директа и предупреждения о тестовой копии выбираются по `mode`, как сейчас по выбору.
- `Wizard.tsx` теряет состояние выбранного режима.

**6. Без перехода к настоящему запуску.**
- `go_real` уходит из `SimulationControl` и из `leaveSimulation` worker.
- `POST /api/simulation` добавляет `go_real` в список устаревших действий: `410 SIMULATION_ACTION_GONE`.
- В меню плеера остаются «Начать заново» и «Новая кампания».
- `store.reopenWizard` остаётся, только если его использует что-то ещё; иначе удаляется вместе с тестами.

**7. Email.** `Store.ownerEmail` бросает ошибку, если у владельца нет email. Демо-бизнесы всегда в симуляции, писем не шлют, так что ошибка значила бы нарушение правила режима, и молча терять её нельзя. Уборка удалённых аккаунтов учитывает `email IS NULL`: у демо нечего обезличивать.

**8. Стартовая страница.**
- `LoginCard` — одна панель по центру на фоне «Рекламы»: те же токены, панели и типографика (`globals.css`).
- Состав: логотип, заголовок «Реклама в Яндексе — без настройки», строка «Сервис сам пишет объявления и ведёт рекламу по вашему бюджету», кнопки «Демо-режим» и «Войти через Google», строка «Демосервис без оплаты · деньги не списываются». Всего меньше 30 слов.
- `ProductMock`, список преимуществ и `.landing`-стили, которые больше нигде не нужны, удаляются.
- Форма тестового входа остаётся под карточкой при `AUTH_TEST_LOGIN=enabled`.
- `TestModeBanner` остаётся.

**9. Выход из демо.**
- `AppHeader` получает `demo: boolean` из `(app)/layout.tsx` (по `accountMode`).
- В демо «Выйти» открывает `Modal.confirm`: «Если выйти, вернуться в это демо не получится», кнопки «Выйти» и «Остаться». Выход — тот же `signOutAction`.
- Для остальных аккаунтов выход без подтверждения, как сейчас.

## Risks / Trade-offs

- [Публичная кнопка создаёт аккаунты без ограничений: бот может заполнить базу демо-аккаунтами и тратить модель на каждом, в пределах лимитов на бизнес] → решение отложено по выбору владельца. В `production-rollout` добавляется задача: до выхода в production — лимит, капча или общий потолок расходов и уборка брошенных демо.
- [Владелец демо теряет данные, если очистит cookie или выйдет] → предупреждение при выходе; другого способа вернуться нет, это свойство демо, и оно записано в спецификации.
- [Без Google нет пути к настоящей рекламе: режим «Яндекс Директ» доступен только тестовому входу на стендах] → так решил владелец («пока недоступно»). Код Директа и его тесты остаются, e2e настоящего режима идёт тестовым входом.
- [Бизнесы в симуляции у аккаунтов тестового входа (стенды) теряют «Запустить по-настоящему»] → миграция описана в дельте `simulation-mode`: «Новая кампания» запускает их уже в Директе.
- [Изменение правит требования, которые есть только в открытых изменениях] → архивировать после `improve-product-clarity-and-trust`, `minimize-interface-load`, `simulation-studio`, `one-screen-simulation`, `simulation-on-owner-numbers`, `new-campaign-in-simulation` и `network-ad-images`. Иначе `openspec archive` отклонит дельты (`validate --strict` предупреждает об этом как INFO).

## Migration Plan

1. Миграция `users` (`kind`, `email` nullable, `CHECK`). Она только добавляет, существующие строки заполняются в той же миграции. Сначала миграция, потом web и worker.
2. Web и worker обновляются вместе: старый worker с `go_real` безвреден, потому что web больше не отправляет это действие, а новый web отклоняет его сам.
3. На стенде из конфигурации web уходят `AUTH_GOOGLE_ID` и `AUTH_GOOGLE_SECRET` (`docs/development.md`).
4. Откат: вернуть код. Колонки `kind` и nullable `email` старый код не читает; демо-строки без email старый код не создаёт, но читал бы их как строки с пустым email только в `ownerEmail`, которого у симуляции не бывает.
