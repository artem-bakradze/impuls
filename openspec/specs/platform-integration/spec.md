# platform-integration Specification

## Purpose

Подключение рекламного аккаунта Яндекс Директа пользователя и все операции с кампаниями через прямой API Директа. Слой площадки изолирован, чтобы позже подключить вторую площадку.

## Requirements

### Requirement: Подключение аккаунта Директа
The system SHALL подключать собственный аккаунт Яндекс Директа пользователя через Яндекс OAuth с доступом к API Директа и Метрики. Подключение SHALL идти через OAuth-приложение Яндекса для авторизации пользователей с адресом возврата в сервисе; приложение для ручной отладки MUST NOT использоваться для подключения пользователей. Запрос авторизации MUST содержать одноразовый параметр `state`, привязанный к сессии пользователя, и ответ с несовпадающим или повторно использованным `state` MUST отклоняться. Токены MUST храниться в зашифрованном виде и обновляться автоматически. Агентские аккаунты и аккаунты в валюте, отличной от рубля, в MVP SHALL отклоняться с понятным объяснением.

#### Scenario: У пользователя нет аккаунта Директа
- **WHEN** пользователь авторизовался в Яндексе, но аккаунта Директа у него нет
- **THEN** система показывает пошаговую инструкцию со ссылкой на создание аккаунта и проверяет его появление при нажатии «Я создал аккаунт»

#### Scenario: Токен отозван
- **WHEN** запрос к API возвращает ошибку авторизации
- **THEN** система приостанавливает автоматические действия по этому пользователю, показывает на сводке «Потерян доступ к Яндекс Директу — подключите заново» и отправляет уведомление на email; кампании продолжают работать с последними настройками и лимитами в Директе

#### Scenario: Пользователь отказался от доступа
- **WHEN** пользователь на странице Яндекса нажал «Отмена» вместо «Разрешить»
- **THEN** система возвращает его на шаг подключения с текстом «Без доступа к Яндекс Директу мы не сможем запустить рекламу» и кнопкой повторного подключения, а токен не сохраняется

#### Scenario: Подложный ответ авторизации
- **WHEN** на адрес возврата приходит ответ с параметром `state`, который не выдавался этой сессии или уже был использован
- **THEN** система не обменивает код на токен, ничего не сохраняет и показывает «Не удалось подключить Яндекс Директ — попробуйте ещё раз»

### Requirement: Данные для маркировки рекламы
The system SHALL перед первым запуском проверять, что в аккаунте пользователя заполнены данные рекламодателя для маркировки через Яндекс ОРД. Если площадка не предоставляет такую проверку через API, система SHALL показывать инструкцию со ссылкой на нужный раздел кабинета и обрабатывать соответствующие ошибки API.

#### Scenario: Директ отклонил запуск из-за маркировки
- **WHEN** API возвращает ошибку, связанную с данными рекламодателя или маркировкой
- **THEN** система показывает «Яндексу нужны данные о вашем бизнесе для маркировки рекламы» со ссылкой на раздел кабинета и повторяет запуск после нажатия «Готово»

### Requirement: Структура создаваемых кампаний
The system SHALL создавать в Директе для каждого «направления» отдельную кампанию. Направление — это пара «группа услуг × канал»; каналы — «Поиск» и «Сайты-партнёры» (РСЯ). Кампания направления «Поиск» MUST показываться только в поиске, кампания направления «Сайты-партнёры» — только на сайтах-партнёрах. Каждой кампании SHALL назначаться:
- зона показа: регион Директа, соответствующий городу бизнеса;
- расписание по часам работы бизнеса;
- цели Метрики;
- лимит расходов, выставленный `budget-guard`;
- мониторинг доступности сайта: площадка приостанавливает показы, если посадочная страница не открывается.

Внутри каждой кампании система SHALL создавать группу объявлений с зоной показа кампании. Для направления «Поиск» группа MUST содержать хотя бы одну ключевую фразу и минус-фразы из `ad-creatives`; без ключевых фраз поисковое направление MUST NOT создаваться. Каждое объявление MUST вести на собственный сайт бизнеса со ссылкой, размеченной UTM-метками сервиса, по которым обращения сопоставляются с направлением и объявлением.

Стратегия с оплатой за обращения SHALL назначаться только вместе с целью Метрики, по которой считаются обращения, и целевой стоимостью обращения, равной ЦСО из `optimization-engine`. Если у бизнеса нет цели Метрики, команда на эту стратегию MUST отклоняться с причиной «нет цели для подсчёта обращений», а кампания остаётся на прежней стратегии.

Доступность сайта проверяет мониторинг Директа. Собственной периодической проверки посадочных страниц сервис MUST NOT выполнять. Остановку показов мониторингом сервис SHALL узнавать из статусов кампаний при сверке и показывать на сводке. Все кампании, созданные сервисом, MUST помечаться так, чтобы сервис отличал их от кампаний, созданных пользователем вручную. Кампании, созданные не сервисом, MUST оставаться нетронутыми.

#### Scenario: В аккаунте уже есть ручные кампании
- **WHEN** у пользователя в Директе есть кампании, созданные не сервисом
- **THEN** система их не изменяет, не останавливает и не учитывает в бюджете сервиса, а на шаге подключения предупреждает, что их расходы не входят в бюджет сервиса

#### Scenario: Посадочная страница не открывается
- **WHEN** сайт пользователя перестал открываться, и Директ приостановил показы мониторингом
- **THEN** не позднее следующей сверки сводка показывает «Ваш сайт не открывается — показы приостановлены, чтобы не тратить деньги впустую», а письмо не отправляется

#### Scenario: Город бизнеса
- **WHEN** пользователь запускает рекламу с городом «Казань»
- **THEN** все кампании сервиса и их группы создаются с регионом «Казань» из справочника регионов Директа

#### Scenario: Запуск поискового направления
- **WHEN** пользователь запускает направление «Маникюр — Поиск» с 12 ключевыми фразами, 5 минус-фразами и двумя объявлениями
- **THEN** в Директе появляется кампания с показами только в поиске, одной группой с регионом города бизнеса, 12 ключевыми и 5 минус-фразами и двумя объявлениями, ссылки которых ведут на сайт бизнеса с UTM-метками этого направления и объявления

#### Scenario: Запуск направления «Сайты-партнёры»
- **WHEN** пользователь запускает направление «Маникюр — Сайты-партнёры»
- **THEN** в Директе появляется кампания с выключенными показами в поиске и включёнными на сайтах-партнёрах, а ключевые фразы для её запуска не требуются

#### Scenario: Поисковое направление без ключевых фраз
- **WHEN** для направления «Поиск» не подобрано ни одной ключевой фразы
- **THEN** кампания не создаётся, а пользователь видит «Не получилось подобрать поисковые запросы для этой услуги — уточните описание услуги»

#### Scenario: Стратегия с оплатой за обращения без цели Метрики
- **WHEN** агент предлагает перевести направление на оплату за обращения, а у бизнеса нет цели Метрики
- **THEN** команда отклоняется с причиной «нет цели для подсчёта обращений», стратегия кампании в Директе не меняется, а в журнале хода записан отказ

### Requirement: Надёжность вызовов API
The system SHALL соблюдать балльные и технические лимиты API Директа. При временных ошибках система SHALL повторять только идемпотентные запросы (чтение, а также изменения с проверкой текущего состояния перед повтором), не больше 5 попыток с экспоненциальной задержкой, записывая каждую попытку в журнал. После исчерпания попыток операция MUST завершаться явной ошибкой. Система SHALL записывать журнал всех запросов и ответов API не меньше чем за последние 3 суток (требование Яндекса к приложениям).

#### Scenario: Исчерпаны баллы API
- **WHEN** API сообщает об исчерпании баллов
- **THEN** система откладывает несрочные операции до восстановления баллов и выполняет операции защиты бюджета в первую очередь

### Requirement: Сверка с кабинетом Директа
The system SHALL не реже раза в час проверять, менялись ли кампании сервиса в обход сервиса — в кабинете Директа или самой площадкой, — и сравнивать фактические настройки с ожидаемыми. Изменения, которые могут увеличить расходы (лимит расходов, стратегия, включение кампании или объявления), MUST проверяться `budget-guard` и урезаться до допустимых. Остальные изменения SHALL приниматься как текущее состояние. Каждое обнаруженное изменение MUST записываться в историю изменений с автором «Изменено в кабинете Директа». Корректировки статистики, о которых сообщает площадка, SHALL вызывать перезагрузку статистики затронутых кампаний. После недоступности сервиса сверка SHALL выполняться раньше остальных задач.

Перед выполнением любой команды система MUST сверять ожидаемое состояние объекта с фактическим. При расхождении команда агента или страховочного правила MUST отклоняться, а при откате пользователю SHALL показываться, что изменилось, с выбором: вернуть сохранённое состояние или отказаться.

#### Scenario: Текст изменён в кабинете
- **WHEN** пользователь отредактировал текст объявления сервиса в кабинете Директа
- **THEN** при ближайшей сверке система принимает новый текст как текущий и записывает в историю «Текст объявления изменён в кабинете Директа» с «было → стало»

#### Scenario: Состояние изменилось перед командой
- **WHEN** агент ставит на паузу объявление, которое пользователь уже остановил в кабинете
- **THEN** команда не выполняется, агент получает причину «состояние объекта изменилось», а изменение из кабинета записывается в историю при сверке

#### Scenario: Корректировка статистики
- **WHEN** Директ сообщает о корректировке статистики кампании за прошлые дни
- **THEN** система перезагружает статистику этой кампании за затронутые дни, не дожидаясь ежедневной перезагрузки

### Requirement: Отслеживание модерации и баланса
The system SHALL не реже раза в час проверять статусы модерации объявлений и баланс аккаунта.

#### Scenario: Объявление отклонено модерацией
- **WHEN** Директ отклонил объявление
- **THEN** система показывает причину простым языком, создаёт исправленный вариант через `ad-creatives` и отправляет его на повторную проверку не более двух раз, после чего просит пользователя отредактировать текст

#### Scenario: Заканчиваются деньги на балансе
- **WHEN** остатка на балансе Директа хватит меньше чем на 3 дня при текущих расходах
- **THEN** система показывает на сводке «Пополните баланс в Яндекс Директе — денег хватит примерно на N дн.» со ссылкой на пополнение и отправляет email

### Requirement: Расширяемость площадок
The system SHALL работать с площадками через единый внутренний контракт: создание и изменение кампаний и объявлений, пауза и возобновление, изменение лимитов, получение статистики и статусов. Подключение второй площадки MUST не требовать изменений в ограничителях оптимизации, инструментах агента, защите бюджета, истории изменений и интерфейсе сводки. Возможности, которые различаются между площадками (например, доступные стратегии), SHALL объявляться адаптером площадки.

#### Scenario: Подключение второй площадки
- **WHEN** разработчик добавляет адаптер VK Рекламы, реализующий контракт
- **THEN** агент, ограничители, защита бюджета и сводка работают с её кампаниями без изменения своего кода

### Requirement: Режимы симулятора и боевого API
The system SHALL поддерживать два режима окружения для работы с Директом: симулятор рекламного рынка и боевой API Директа. Режим окружения задаётся конфигурацией, а не пользователем, и определяет, куда идёт режим бизнеса «Яндекс Директ». Режим бизнеса «Симуляция» (`simulation-mode`) от режима окружения не зависит: он выбирается пользователем и всегда работает на симуляторе с виртуальным временем, в том числе в боевом окружении. Локальная разработка, CI и staging SHALL работать в режиме симулятора. Конфигурация с неизвестным режимом, в том числе с прежним значением режима песочницы, MUST отклоняться при старте с явной ошибкой. В режиме симулятора интерфейс MUST постоянно показывать плашку «Тестовый стенд — Яндекс Директ не подключён, реклама не показывается»; на экранах бизнеса в режиме «Симуляция» её заменяет пульт симуляции со своей пометкой, чтобы на экране не было двух плашек о ненастоящей рекламе.

#### Scenario: Окружение разработки
- **WHEN** сервис запущен в режиме симулятора
- **THEN** ни один вызов не уходит в API Директа, кампании создаются в симуляторе, а на каждой странице видна плашка тестового стенда или, у бизнеса в симуляции, пульт симуляции

#### Scenario: Устаревшая конфигурация песочницы
- **WHEN** сервис запускается с режимом песочницы, оставшимся от прежней конфигурации
- **THEN** worker и web не стартуют и сообщают, что режим песочницы больше не поддерживается и допустимы только режимы симулятора и боевого API

#### Scenario: Боевой режим
- **WHEN** сервис запущен в режиме боевого API
- **THEN** все вызовы бизнесов в режиме «Яндекс Директ» идут в боевой API Директа от имени подключённого аккаунта пользователя, а плашка тестового режима не показывается

#### Scenario: Симуляция в боевом окружении
- **WHEN** в боевом окружении пользователь запускает бизнес в режиме «Симуляция»
- **THEN** кампании этого бизнеса создаются только в симуляторе, ни один вызов не уходит в API Директа, а бизнесы в режиме «Яндекс Директ» продолжают работать с боевым API

### Requirement: Разрезы статистики, минус-фразы и корректировки в Директе
The system SHALL получать у площадки статистику кампаний сервиса за период в разрезе поисковых запросов и в разрезе устройств — телефоны, компьютеры, планшеты. Разрезы считаются так же, как дневная статистика: с НДС, с той же атрибуцией и обращениями по той же цели Метрики. Сумма расходов и обращений по строкам разреза за период MUST совпадать с дневной статистикой кампании с точностью до округления и запросов, скрытых площадкой.

The system SHALL уметь через исполнитель команд:
- задавать список минус-фраз кампании целиком;
- задавать корректировки ставок кампании для телефонов и для компьютеров.

Текущие значения обеих настроек SHALL читаться у площадки для проверки ожидаемого состояния перед изменением. Изменения этих настроек в кабинете Директа SHALL обнаруживаться сверкой и попадать в историю с автором «Изменено в кабинете Директа» (`Требование: Сверка с кабинетом Директа`).

Ограничения:
- вызовы MUST касаться только кампаний, созданных сервисом;
- запросы и ответы MUST попадать в журнал вызовов без токенов, как остальные вызовы;
- симулятор SHALL реализовывать те же операции (`testing-harness`).

#### Scenario: Минус-фраза дошла до Директа
- **WHEN** исполнитель применяет команду добавить минус-фразу «бесплатно» к рекламе в поиске
- **THEN** список минус-фраз кампании в Директе содержит «бесплатно» вместе с прежними, а запись истории хранит список до и после

#### Scenario: Корректировка изменена в кабинете
- **WHEN** владелец сам поменял корректировку для телефонов с −30% на 0% в кабинете Директа
- **THEN** сверка находит расхождение, в истории появляется запись автора «Изменено в кабинете Директа» с «было −30% → стало 0%», и следующая команда агента проверяет ожидаемое состояние по новому значению

#### Scenario: Разрез совпадает с дневной статистикой
- **WHEN** за 14 дней дневная статистика кампании — 9 800 ₽ и 21 обращение
- **THEN** сумма строк разреза по устройствам за те же дни — 9 800 ₽ и 21 обращение с точностью до 1 ₽ на строку
